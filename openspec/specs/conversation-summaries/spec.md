# Conversation Summaries

## Purpose

Automatically generates structured conversation summaries after each session, stored as working-tier memories for future context. Summaries are progressively consolidated by memory maintenance to keep the working set bounded.

## Requirements

### Requirement: Auto-Generation After Session

The system SHALL automatically generate a conversation summary after each session that produces at least one reply via `send-reply`. The summary SHALL be generated on the same ACP session before disconnect.

#### Scenario: Summary generated after reply
- **GIVEN** a session has sent at least one reply
- **WHEN** the session completes (agent returns `end_turn`)
- **THEN** the system SHALL generate a conversation summary on the same ACP session
- **AND** store it as a memory event in the user's workspace

#### Scenario: No summary for sessions without reply
- **GIVEN** a session completes without sending any reply
- **WHEN** session cleanup begins
- **THEN** no conversation summary SHALL be generated

### Requirement: Summary Memory Attributes

Conversation summaries SHALL be stored with `tier: "working"` and `category: "summary"`. The `scope` SHALL be `"user"` (stored in the user's personal workspace).

#### Scenario: Summary storage attributes
- **WHEN** a conversation summary is saved
- **THEN** the memory event SHALL have `tier: "working"`
- **AND** `category: "summary"`
- **AND** `scope: "user"`
- **AND** `visibility: "public"`

### Requirement: Summary Content Structure

Each conversation summary SHALL contain: timestamp range (session start to end), participant count, key topics discussed, decisions made or action items, and emotional tone of the conversation.

#### Scenario: Summary includes required fields
- **GIVEN** a session spanning 10 minutes with 2 participants discussing project deadlines
- **WHEN** the summary is generated
- **THEN** the summary content SHALL include the timestamp range
- **AND** participant count
- **AND** key topics (e.g., "project deadlines")
- **AND** any decisions or action items identified
- **AND** the emotional tone (e.g., "focused", "casual")

### Requirement: Summary Generation Reuses ACP Session

The summary SHALL be generated by sending an additional prompt on the same ACP session that handled the conversation. The system SHALL NOT create a new agent connection for summary generation.

#### Scenario: Same session reuse
- **GIVEN** a conversation session with ID `sess_abc` has completed its reply
- **WHEN** summary generation is triggered
- **THEN** the summary prompt SHALL be sent via `connector.prompt(sess_abc, ...)`
- **AND** no new ACP session SHALL be created

### Requirement: Summary Generation Failure Is Non-Fatal

If summary generation fails (agent error, timeout, etc.), the failure SHALL be logged but SHALL NOT affect the already-sent reply or crash the session.

#### Scenario: Summary failure does not block reply
- **GIVEN** a session has successfully sent a reply
- **WHEN** summary generation throws an error
- **THEN** the error SHALL be logged
- **AND** the session SHALL complete normally
- **AND** the previously sent reply SHALL remain delivered

### Requirement: Progressive Consolidation by Maintenance

Memory maintenance SHALL consolidate older working-tier summaries into fewer archive-tier entries. The consolidation SHALL preserve key information while reducing the total count of working-tier summaries.

### Requirement: Configurable Summary Model

The system SHALL support a `conversationSummary.model` configuration to specify which model generates conversation summaries. The system SHALL switch the ACP session model before sending the summary prompt and restore the original model afterward. If `conversationSummary.model` is not configured, the system SHALL use the default `agent.model` without any model switch.

#### Scenario: Summary uses configured model
- **GIVEN** `conversationSummary.model` is set to `"gpt-5-mini"`
- **AND** `agent.model` is set to `"claude-opus-4.6"`
- **WHEN** summary generation is triggered after a successful session
- **THEN** the system SHALL call `connector.setSessionModel(sessionId, "gpt-5-mini")` before the summary prompt
- **AND** the summary prompt SHALL be sent on the switched model
- **AND** the system SHALL call `connector.setSessionModel(sessionId, "claude-opus-4.6")` after the summary completes

#### Scenario: Default model when not configured
- **GIVEN** `conversationSummary.model` is not configured
- **AND** `agent.model` is set to `"claude-opus-4.6"`
- **WHEN** summary generation is triggered
- **THEN** no `setSessionModel` call SHALL be made
- **AND** the summary prompt SHALL be sent on the current `"claude-opus-4.6"` model

#### Scenario: Original model restored after summary
- **GIVEN** `conversationSummary.model` is set to `"gpt-5-mini"`
- **WHEN** summary generation completes (success or failure)
- **THEN** the system SHALL restore the original model via `setSessionModel`
- **AND** subsequent operations on the session SHALL use the original model

#### Scenario: Summaries consolidated during maintenance
- **GIVEN** a workspace has 20 working-tier summaries older than 7 days
- **WHEN** memory maintenance runs
- **THEN** the agent SHALL consolidate related summaries into archive-tier entries
- **AND** the original summaries SHALL be disabled via `memory-patch`
- **AND** consolidated entries SHALL include `supersedes` referencing the original IDs
