## Why

Design §7 makes restricted execution conditional on an authenticated, client-observable readiness result for the exact current ACP session and process instance, and §10 step 5 sequences it after gate-context registration and model/reasoning setup, before the first normal prompt. P0 recorded policy readiness as **Partial support, overall unresolved** — synchronous trusted-handler registration and `tool_call`/source-metadata surfaces exist, and the lifecycle runner reports init failures while tool-call errors/timeouts fail closed — but the complete narrow authenticated control channel and the native-to-ACP identity binding remain UNRESOLVED. Row 13 ships the readiness SIGNAL and the client DECISION (deny until ready) around that unresolved channel with an explicit unresolved-gate marker, so restricted sessions are blocked-by-default rather than optimistically allowed.

## What Changes

- **Readiness signal inside the row-12 trusted module**: the restricted `tool_call` enforcement handler is installed synchronously during trusted-module loading (row 12's module; this row defines only the readiness SIGNAL it emits — the policy content is row 14). Each restricted session's readiness state initializes to FALSE and becomes ready only through an authenticated establishment for the exact `(process instance, ACP session)` tuple.
- **Client-observable authenticated readiness contract**: a readiness result bound to the current process instance, ACP session ID, restricted mode, fresh challenge, policy revision, and registry epoch (P0's `ReadinessContract`), authenticated with process/session-scoped material that MUST NOT reuse the raw platform token or the raw Skill API server secret and CANNOT be asserted by chat content. Mechanism honesty per pinned source: the lifecycle-init failure signal is `supported`; a narrow authenticated control channel and the native-to-ACP identity mapping are `candidate-to-verify`/`no-supported-mechanism` exactly as P0 recorded — labeled, not inflated.
- **Client prompt gate (design §10 step 5, §13)**: before the FIRST normal prompt of a restricted OMP session (after gate-context registration + model/reasoning set), the connector verifies readiness for that exact session+process; not ready → the session is denied with an ACP-visible bounded rejection diagnostic (`readiness_rejected` lineage), never falling back to an unguarded process. Lifecycle-handler failure, timeout, or partial initialization leaves restricted execution BLOCKED. `session/new`/`session/load` success alone NEVER establishes readiness — asserted explicitly.
- **Reset + re-verify on every transition**: new/load/recovery AND post-start operator-MCP tool-registry refresh reset readiness (not a one-shot startup ack); row 11's `onGateContextRestored` hook is ATTACHED to without relocating row 11's gate-context restore; recovery readiness re-verification is this row's. A prior process instance's acknowledgement is never reused across a respawn. Row 12's ownership/readiness event surfaces (`session_start`, initial snapshot, resource-generation checks) are consumed, never duplicated.
- **Scope honesty**: this is a narrow machine-controlled readiness signal, explicitly NOT a human form-elicitation/approval UI (design §5 non-goal). The gate applies ONLY to restricted OMP sessions — native-YOLO OMP has no restricted policy to be ready (design D6), and OpenCode is entirely unaffected.
- **Unresolved-gate marker + explicit user-decision language** exactly like rows 8/9/12: where P0 left the control channel / identity binding unresolved, the shipped gates stand open; unit/mock tests validate the client DECISION LOGIC and the module's readiness-SIGNAL contract, NEVER that the native binary emits or verifies real readiness. Synthetic ready-fixtures cannot clear the gate.
- Explicit non-goals (owned elsewhere): restricted tool inventory/provenance/default-deny policy + alternate URI/device blocking + destructive wiring (`enforce-omp-restricted-tool-policy`, row 14); pre-import exclusion internals + critical-skill selection (`guard-omp-executable-discovery`, row 12 — landed, consumed); LSP disablement (`disable-restricted-agent-lsp`, row 15); transport (`control-omp-url-fetch-transport`/`adapt-omp-web-search`/`adapt-omp-public-code-search`, rows 17–19); packaging (`package-pinned-omp-runtime`, row 20). Gate-context registration/restore is row 4/row 11 (consumed); mode resolution is row 10 (consumed); the trusted module and its launch flags are row 9/row 12 (consumed).
- No new `config.yaml`, `.env`, or Helm field: readiness inputs are in-process state, the pinned ACP stdio connection, and row-12 module state — source constants and existing plumbing. `config.example.yaml`, `.env.example`, and `helm/values.yaml` are intentionally unchanged; if implementation surfaces any new field, this change synchronizes all three itself.
