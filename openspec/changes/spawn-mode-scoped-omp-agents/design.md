## Context

`createAgentConfig()` (`src/acp/agent-factory.ts`) currently has one branch (`"opencode"`) plus a default `throw`; row 7 widened `AgentType` to `"opencode" | "omp"` with a shared predicate and an `omp` credential set, and row 8 produced `ompSettingsForMode("restricted" | "native-yolo")` returning `{ overlayFiles: {path, content}[], modelsYamlContent, systemPromptSourcePath, providerEnvKeys, envPosture }` plus the unresolved record-reset gate. Constraints: approved design §5 (mode isolation, `PI_CODING_AGENT_DIR` under the process `TMPDIR/omp-agent`, process state vs payload staging), §7 (owned overlays above project config, exact `--trusted-extension`, no hostile-layer inheritance), §12 (credential set, prompt mapping, no invented fields); row 7's never-pass filter and its explicitly deferred `XDG_DATA_HOME` decision; row 8's ordering contract (shared-first, mode document last, `PI_CONFIG_FILES` never exported, deployment-owned cwd/global dir); P0's unresolved verdicts. OpenCode's branch and `getSessionModeOverride("opencode", true) === "yolo"` are regression-protected. Real `omp` binaries are absent in development environments (row 20), so every acceptance decision is observable through unit/mock inspection of the assembled `AgentConfig`.

## Goals / Non-Goals

**Goals:** A factory `omp` branch that deterministically assembles both mode launches from row 8 selectors; mode-distinct process state/TMPDIR/cwd ownership that holds regardless of pool-key composition; the canonical Skill API staging location provably untouched; the trusted-extension module referenced by one exported path with fail-closed absence behavior; sandbox/egress pass-through identical to OpenCode's; consumer-visible tests for every proposal claim; OpenCode zero-regression.

**Non-Goals:** Pool identity/acquisition (row 10), reconnect/`session/load`/gate-context restore (row 11), the extension module's content, pre-import exclusion, and provenance bootstrap (row 12), readiness gating (row 13), `tools.approval` records/tool inventory (row 14), LSP implementation (row 15), staging prompt text (row 16), fetch/search transport (row 17), binary/overlay/module installation, checksums, version health (row 20), native runtime execution, live-provider or container acceptance, any P0/row-7/row-8 contract edit, any new config/env/Helm field.

## Decisions

### 1. Mode resolves from the existing `yolo` argument at spawn; nothing else

`createAgentConfig(type, workingDir, appConfig, yolo, …)` already receives the effective permission mode at spawn (the orchestrator resolves YOLO before acquisition per design §10). The `omp` branch maps `yolo === false => "restricted"`, `yolo === true => "native-yolo"` and calls `ompSettingsForMode` once. `getSessionModeOverride()` gains no `omp` case: `("omp", *)` returns `null` exactly as today (the existing `if (agentType === "opencode" && yolo)` already yields this), locked by test rather than by new branching code. Rationale: design D7/D8 — OMP mode is a spawn fact, never an ACP `setSessionMode()` call; adding an `omp` case or a runtime toggle would recreate the mixed-mode process the design prohibits. Alternative rejected: passing `--yolo`-style CLI flags plus mode switching — the flag-only half is fine but mode switching would let one process serve both postures.

### 2. Argument assembly is ordering-consumed from row 8, never re-derived

Restricted: `["acp", "--no-extensions", ...row8.orderedConfigArgs, "--trusted-extension", OMP_TRUSTED_EXTENSION_PATH, "--system-prompt", row8.systemPromptPath]` where `orderedConfigArgs` interleaves `--config` with row 8's ordered paths (restricted mode document last among deployment overlays, owned `models.yml` per row 8's composition). Native-YOLO: the identical shape with the native-yolo composition — which by row 8 §8 cannot contain `tools.approval*`, `lsp.*`, or `disabledProviders` — so "no restricted clamps" (design D6) is enforced by composition plus an assembly-time assertion that the resolved YOLO `--config` file set is disjoint from the restricted set. The approval mode is never a CLI flag: row 8's `tools.approvalMode` pin (restricted `write`, yolo `yolo`) is the only carrier, satisfying "pin a non-YOLO native approval mode rather than relying on an implicit default" without inventing a flag. No `--yolo`/auto-approve flag appears in either branch's restricted-shaped test; the no-flag invariant is asserted on the restricted args. Alternative rejected: deriving overlay paths by globbing `agent-config/omp/` — ordering and mode membership are row 8 contracts; globbing forks them.

### 3. Process state ownership lives in a new pure `omp-paths.ts`, mirroring `opencode-paths.ts`

New `src/utils/omp-paths.ts` exports pure helpers: `ompProcessStateRoot(stateRoot, mode)` (`{stateRoot}/omp-agent`), `ompAgentDir(stateRoot, mode)` (`…/omp-agent/{restricted|native-yolo}` → `PI_CODING_AGENT_DIR`), `ompProcessTmpDir`, `ompLaunchCwd`, `ompXdgDataHome` (all mode-segmented under the same roots). Inputs follow OpenCode's existing root selection: pool/shared processes root at the bot data root (`appConfig.workspace.repoPath`-derived, like `channel-tmp`/`channel-cwd` today, with the pool key contributing a segment but the mode segment added independently so distinctness never depends on row 10's key formula), per-spawn processes root at the session workspace `tmp` area. The mode segment is ALWAYS present, so even a caller bug that reuses a pool key across modes yields different `PI_CODING_AGENT_DIR`/cwd values (design §5 "incompatible modes must not reuse a state root"). `PI_CODING_AGENT_DIR` points at an empty deployment-owned directory (row 8 §2: global layer must be empty); the factory creates the directory at spawn exactly as `workspace-manager.ts` ensures `tmp/`. Alternative rejected: putting mode into the pool key only — row 10 owns identity, and the intermediate state between rows 9 and 10 must already be safe.

### 4. XDG posture: OMP gets a scoped value; OpenCode is untouched

Row 7 kept `XDG_DATA_HOME` in the base allowlist because the factory always sets it, and deferred the OMP decision here. Resolution: in the `omp` branch the factory sets `XDG_DATA_HOME` under the mode-scoped process state area (`ompXdgDataHome`), so any XDG-basedir-conforming data a tool writes stays inside process-scoped state and never the shared `$HOME/.local/share` root the F12 comment in `opencode-paths.ts` was written to avoid. The OpenCode branch keeps `sessionXdgDataHome(workingDir, sessionId)`/pool-derived values byte-identically (regression test). `XDG_CONFIG_HOME`/`XDG_STATE_HOME`/`XDG_CACHE_HOME`, `OMP_PROFILE`, `PI_PROFILE`, `PI_CONFIG_FILES` are NEVER set by the factory; row 7's filter drops them if the deployment environment carries them, and the OMP branch additionally never populates them into the base env (defense in depth, tests for both layers). The launch `cwd` is the mode-segmented neutral directory — never a user workspace — so OMP's project layer (`<cwd>/.omp/` only, no ancestor walk-up) is empty by construction; per-session `newSession.cwd` still carries user workspaces as with OpenCode.

### 5. Canonical payload staging is explicitly independent of process state

Design §5 separates "process `TMPDIR`/state ownership" from "session payload staging". The factory changes NOTHING about staging: `RetryPromptContext.stagingDir` (`{workspace}/tmp/{sessionId}` built by the orchestrator), `ChatbotClient.resolveSessionPath()` token expansion, and the Skill API's canonical session root remain the authority. The `omp` branch sets the process `TMPDIR` env var to `ompProcessTmpDir` (shared/pool) or the session `tmp` (per-spawn, same as OpenCode today), and the distinctness tests assert (a) the OMP `TMPDIR`/`PI_CODING_AGENT_DIR` are mode-distinct while (b) the staging path derived from the workspace is identical for restricted and YOLO spawns of the same session — i.e. payload containment never reads the mode-partitioned root. Alternative rejected: staging under the mode-partitioned TMPDIR — it would fork the Skill API path contract that row 16 later makes absolute.

### 6. Trusted-extension path is a constant selector with fail-closed launch, zero trust logic

`omp-paths.ts` exports `OMP_TRUSTED_EXTENSION_PATH` — the contracted deployment-owned, agent-non-writable module path (same owned tree as row 8's overlays, final install location coordinated with row 20; development-tree source path constant until row 20's install lands). The factory performs only presence selection: it never copies, mutates, or trusts content; rows 12/13 own what the module IS and when it is trusted. If the path is absent at spawn, the OMP branch throws (design §13: missing owned configuration/trusted-module initialization fails the affected session; no unguarded fallback, no silent downgrade to plain `omp acp`, no OpenCode fallback — row 7's config acceptance never implied launch support). Unit tests assert the flag carries exactly the constant and that a missing-module fixture throws; row 20 must place the module at this path (checksums there), row 12 extends from it. Alternative rejected: a new config field for the path — a configurable trusted path would let workspace-adjacent config redirect trust; a source constant is the only non-widening choice, and row 20 already owns the install location.

### 7. Env and egress pass through the existing pipeline unchanged

The `omp` branch builds the same base env categories as OpenCode (inherit essentials, `AGENT_WORKSPACE`, `SKILL_JWT_DIR`, `SKILL_SHARED_PROCESS` for pool spawns, per-spawn-only `SESSION_ID`, `AGENT_BROWSER_EXECUTABLE_PATH` detection, `GEMINI_API_KEY`/`OPENROUTER_API_KEY` from row 7's set — no `GOOGLE_GENERATIVE_AI_API_KEY`, no `OPENCODE_API_KEY`) plus OMP state vars, then returns through the UNCHANGED `SandboxManager.buildSpawnOptions` path (`createAgentConfig` already wraps `buildBaseAgentConfig` output), so `filterEnv`, `egressProxy`/`unrestrictedEgress`/`networkIsolation` resolution, proxy URL + `NO_PROXY` composition, bwrap confinement, and unshare wrapping apply identically (design §9). No mode-conditional network behavior: the YOLO OMP process gets the same egress posture as its restricted sibling (design D6's permissiveness is tool-level native behavior, not a network rule); transport adaptation is row 17. Because `--trusted-extension`/`--config` files must stay readable inside bwrap confinement, the confinement inputs (owned roots outside agent-writable paths) are asserted compatible in tests via the existing `buildBwrapConfinement` argument capture — no confinement code changes here. Alternative rejected: an OMP-specific sandbox manager — a second filter/egress convention is exactly the "second allowlist" design §4 forbids.

### 8. `omp` binary resolution is plain PATH

Command is `"omp"`, spawned with `clearEnv` like every agent; row 20 installs `/usr/local/bin/omp` from the pinned release. No binary-path config field is added (a deployment-configurable launch target for a security-pinned binary invites override; the image owns the path). Tests assert the command string; real PATH resolution is user/runtime-verified. Alternative rejected: `agent.ompBinaryPath` config — rejected for trust-widening and because it would force config/.env/Helm synchronization with no design basis.

### 9. Failure posture and observability

Missing trusted module, missing/unreadable row-8 overlay files, or a composition gate report that says restricted security consumption is blocked (row 8 `recordResetGate`) do not silently downgrade: module/overlay absence throws at spawn; the record-reset gate status is logged at launch (warn) and referenced in docs so operators see the inherited limitation, matching design §13 "no unguarded fallback". Tests cover throw-on-absent-module and warn-not-block for the inherited gate (the gate governs security CLAIMS, and row 14's runtime default-deny is the operative boundary — same reading row 8 shipped).

## Risks / Trade-offs

- **Mode segment duplicating row 10 identity** → mode segment is state-namespace only; row 10 owns pool/process identity. Docs state the split so row 10 does not remove the factory-side distinctness.
- **`TMPDIR` semantic drift for skills** (skills historically see session `tmp`) → per-spawn OMP keeps session `tmp` identical to OpenCode; only pool-mode roots gain mode segments; staging path asserted unchanged, and row 16's absolute-path work never depends on `TMPDIR` values.
- **Row 8 ordering contract drift** → assembly consumes `orderedConfigArgs` opaquely; a row 8 ordering change requires zero factory edit, and the disjointness assertion catches mode-crossing regressions in CI rather than at runtime.
- **Inherited gates misread as launch support** → `docs/OMP_SPAWN.md` repeats the P0/row-8/row-12/20 gate list; tests are mock-only and say so; no requirement here claims native enforcement.
- **Shared `agent-factory.ts` churn across rows 7/8/20** → this change confines its edits to the new `case "omp"` branch plus module-level exports; the OpenCode case body is not restyled, keeping row 7/8/20 merges mechanical.

## Migration Plan

Additive launch branch: until row 20 packages the binary and row 12/20 provide the module, `omp` spawns throw at the fail-closed checks in normal deployment and behave identically in tests; OpenCode is untouched, so rollback is reverting one commit. No state migration, no config change, no compatibility shim.
