## Context

The agent-type decision surface today is five loose conventions rather than one contract: `src/acp/types.ts` declares `export type AgentType = "opencode"`; `src/types/config.ts` declares `defaultAgentType?: "opencode"`; `src/utils/env.ts` maps `AGENT_DEFAULT_TYPE → agent.defaultAgentType` with a plain string coercion in `applyEnvOverrides()` (no validation, empty string skipped); `src/core/config-loader.ts::validateConfig()` never inspects the field, so an unknown value loads successfully and only fails later in `agent-factory.ts::buildBaseAgentConfig()`'s `default:` throw — at first spawn, after the application is running; `src/dashboard/server.ts::handleChatConnect()` re-implements validation as `rawAgentType !== "opencode"`; and the examples say opencode-only in three places (`config.example.yaml:65`, `.env.example:22-23`, `helm/values.yaml:52-53`). `src/acp/sandbox-manager.ts` has a `BASE_ALLOWED_ENV` base set (which includes `XDG_DATA_HOME`, `SKILL_JWT_DIR`, `TMPDIR` and the proxy vars), an `AGENT_TYPE_ENV: Record<string, string[]>` with ONLY an `opencode` key, and `buildFilteredEnv()` which unions base + agent-type keys + `this.config.allowedEnvVars` with no ceiling on that operator-supplied list. Spawns are `clearEnv: true` (connector), so the filtered `AgentConfig.env` is the entire subprocess world.

The approved design (§12) keeps `GEMINI_API_KEY` and `OPENROUTER_API_KEY` as the supported provider credentials, requires filtering platform tokens, dashboard credentials, the raw Skill API server secret, unapproved provider credentials, profile selectors, and security-relevant setting overrides from the child environment, mandates the three-document synchronization whenever config/env fields change, and requires agent-type defaulting/unknown-rejection to be consistent across loader/env/examples. §5 adds the pool-state rule (no named OMP profile, no inherited profile/XDG selectors) whose positive mechanism belongs to rows 8/9. P0 (`establish-omp-compatibility-contracts`) is an application gate for native mechanisms; nothing in this slice needs a new native interface, because the two credential names already exist in the deployment for OpenCode.

## Goals / Non-Goals

**Goals:**

- One supported-agent-type predicate owned in the ACP type module, consumed by the config loader, the dashboard, and factory dispatch, with the type union widened to `"opencode" | "omp"`.
- Load-time validation: omitted => `opencode`; `opencode`/`omp` accepted; everything else => `ConfigError(ErrorCode.CONFIG_INVALID)` naming field and valid values.
- An `omp` credential key set of exactly `GEMINI_API_KEY` + `OPENROUTER_API_KEY`, plus an enforced never-pass category ceiling (platform tokens, dashboard passphrase, raw Skill API secret, provider keys outside the agent's supported set, profile/XDG selectors) that neither the base set nor `allowedEnvVars` can breach.
- All three configuration documents (`config.example.yaml`, `.env.example`, `helm/values.yaml`) describe the `opencode|omp` domain in this change, plus the AGENTS/docs tables.
- Consumer-visible unit tests for every decision: parsing default/valid/unknown from both sources, credential allow/deny per agent type, `allowedEnvVars` ceiling rejection, selector non-inheritance.

**Non-Goals:**

- No OMP launch command, flags, owned settings files/overlays, trusted-module path, `PI_CODING_AGENT_DIR`/process `TMPDIR` assignment, or state-root scoping (rows 8/9); no pool/mode identity (row 10); no provider header/compaction/update-posture translation (row 8); no model-catalog behavior (row 6); no search/network credential expansion (rows 17–19); no packaging/version-health (row 20); no combined lifecycle regression (row 21); no redefinition of P0 contracts; no ACP SDK change; no live agents or container runs.
- No new config/env FIELD: only the accepted value domain of the existing `defaultAgentType`/`AGENT_DEFAULT_TYPE` changes, so no template/helm-secret plumbing change is needed beyond the values/comment text.

## Decisions

**D1 — One predicate, one union, everywhere.** `src/acp/types.ts` gains `export type AgentType = "opencode" | "omp"`, `export const SUPPORTED_AGENT_TYPES: readonly AgentType[] = ["opencode", "omp"]`, and `export function isSupportedAgentType(value: unknown): value is AgentType` (strict: `typeof value === "string"` and membership after `.trim()` must equal the value itself, i.e. `" omp "` and `"OpenCode"` are NOT supported — trimming-normalization belongs to the loader's error message, not to silent acceptance). `src/types/config.ts` narrows to `defaultAgentType?: AgentType`. The loader, the dashboard, and `createAgentConfig()`'s exhaustiveness all consume this module; no second literal list. Alternative considered: validate in `applyEnvOverrides()` in `env.ts` — rejected because the env layer deliberately knows no field semantics (all coercions there are type-only), the config file needs the same rule, and one validation point at final merge (after defaults → base → env-specific → env) is the existing convention for every other rejected field (`replyPolicy`, dashboard passphrase).

**D2 — Loader validation, fail closed, message-shaped like the existing rejections.** In `validateConfig()` next to the `replyPolicy` check: if `agent.defaultAgentType !== undefined` and not `isSupportedAgentType(...)`, throw `new ConfigError(ErrorCode.CONFIG_INVALID, 'Invalid agent.defaultAgentType value: "<v>". Must be one of: opencode, omp', { field: "agent.defaultAgentType", value })`. `getDefaultAgentType()` keeps `?? "opencode"` unchanged (omitted default lives in exactly one place). Empty-string is rejected explicitly — the `${AGENT_DEFAULT_TYPE}` expansion-to-empty-string path in `expandEnvVars()` makes `defaultAgentType: ""` reachable from the shipped example config, and silently treating it as omitted would hide a missing env var behind a working default; `applyEnvOverrides` already ignores an empty env value, so the surviving empty string can only come from the YAML. Non-strings (YAML `true`, numbers) fail the strict predicate. Alternative considered: normalize/trip-and-lowercase the value into acceptance — rejected: design §12 wants unknown-type rejection consistent and explicit, and silent normalization of deployment-level agent selection is the behavior class the loader rejects elsewhere (see P0's "invalid values that fall back to native defaults are not protection").

**D3 — Credential sets stay in `sandbox-manager.ts`; `omp` gets exactly the two supported keys.** `AGENT_TYPE_ENV.omp = ["GEMINI_API_KEY", "OPENROUTER_API_KEY"]`. `OPENCODE_API_KEY`/`GOOGLE_GENERATIVE_AI_API_KEY` stay opencode-only: the latter is an OpenCode-side provider alias AIr sets redundantly for Gemini, and design §12 admits only Gemini/OpenRouter for the supported set (OMP names Gemini's provider `google`; ID translation is row 8's settings work, not an env-filter concern). The base set is unchanged — the existing opencode path must stay byte-identical, which the regression tests assert.

**D4 — Never-pass category ceiling enforced inside `buildFilteredEnv()`.** Today the operator `allowedEnvVars` is appended to the allow-set unchecked, so `AGENT_SANDBOX_ALLOWED_ENV_VARS=DISCORD_TOKEN` would hand the platform token to the agent. Add a module-level `NEVER_PASS_ENV` grouped by category with the explicit names: platform tokens `DISCORD_TOKEN`, `MISSKEY_TOKEN`; dashboard credentials `DASHBOARD_PASSPHRASE`; raw Skill API server secret `AGENT_SKILL_API_SECRET`; unapproved provider keys `OPENCODE_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, `GITHUB_TOKEN`, `COPILOT_GITHUB_TOKEN`, `GIT_BACKUP_AUTH_PASSWORD`; profile/XDG state selectors `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, `OMP_PROFILE`, `PI_PROFILE`, `PI_CODING_AGENT_DIR`. Filtering removes any never-pass name from the union of base + agent-type + operator sets, logging one bounded structured warning per excluded operator-configured name (names only — never values). The base and agent-type sets cannot contain a never-pass name by construction, but the enforcement sits on the final set so a future careless edit to either list is caught by the same tests. Prefix/glob matching is deliberately NOT implemented: an explicit-name list matches every other allowlist convention here and stays reviewable; the categories are named in the spec so future secret names are added deliberately. Alternative considered: a `SECRET`/`TOKEN`-substring heuristic — rejected: nondeterministic, would silently drop legitimate names (`SESSION_TOKEN`-style future harness vars), and creates a second classification convention, which design §4 forbids.

**D5 — `XDG_DATA_HOME` stays in the base allowlist, with its scope documented, not expanded.** It is OpenCode's tool-output scoping mechanism and the factory always sets the value it passes (session-scoped under the session TMPDIR per-spawn, pool-key-scoped in shared mode), so the deployed value is never a raw inherited selector. Design §5's OMP rule is stronger than filtering: scoped OMP state requires `PI_CODING_AGENT_DIR` under the selected process's `TMPDIR/omp-agent` with mode-distinct roots, which only rows 8/9 can establish — this change therefore (a) never passes `PI_CODING_AGENT_DIR`/profile/other-XDG selectors (D4), (b) adds the ADDED spec requirement that an inherited `XDG_DATA_HOME` is not an OMP state grant, and (c) puts an explicit comment at the allowlist entry stating the OMP scoped-state decision is deferred to `translate-omp-owned-settings`/`spawn-mode-scoped-omp-agents`. Pre-empting it here (e.g. dropping `XDG_DATA_HOME` or inventing an OMP-scoped value in the factory) would break the existing OpenCode tool-output boundary or collide with row 9's ownership.

**D6 — Dashboard validates via the shared predicate; no launch claim.** `handleChatConnect()` replaces `rawAgentType !== "opencode"` with `!isSupportedAgentType(rawAgentType)` before the `AgentType` narrowing (keeping the existing 400 shape), so the dashboard cannot drift from the loader. Since `createAgentConfig()` still has no `omp` branch (row 9's launch ownership), an `agentType: "omp"` dashboard request passes validation and then fails connection establishment through the factory error — the delta spec makes that distinction explicit so no test can claim OMP chat works from a 200-shaped validation-only path; tests assert the validator decision, and the orchestrator's existing per-session connection-failure isolation carries the runtime outcome. Alternative considered: reject `omp` in the dashboard until row 9 lands — rejected: it duplicates the type domain in a second place with a temporary rule and would need removal work in row 9; the existing failure isolation makes the honest path safe.

**D7 — `env.ts` stays semantic-free; `omp` documentation lands in all three docs here.** `ENV_MAPPINGS.AGENT_DEFAULT_TYPE` is already the correct mapping and needs no code change; its `applyEnvOverrides` string passthrough plus the loader rejection is exactly the pipeline the other enum-like fields use. `config.example.yaml`, `.env.example` and `helm/values.yaml` each re-comment the field as `opencode` (default) | `omp` with a note that unknown values fail startup; the example default value stays `opencode`. AGENTS.md (line ~616 "Valid value"), `docs/DESIGN.md` and `docs/DEVELOPMENT.md` env tables gain `omp`. This is the batch contract's "ALL THREE config docs updated in THIS change" — no other row in the batch touches config docs, so no serialization risk exists beyond the usual serial `CHANGELOG.md`.

## Risks / Trade-offs

- **[Loader now rejects configs that previously booted]** Any deployment carrying a stray `defaultAgentType` typo or legacy value (`copilot`, `gemini`) previously started and died only at first spawn; it will now fail at startup. Accepted: pre-release, fail-closed at load is the design's posture, and the error names field and valid values.
- **[Empty-string rejection breaks an unset-`${AGENT_DEFAULT_TYPE}` example]** An operator copying the example `defaultAgentType: "${AGENT_DEFAULT_TYPE}"` without the env var now fails to load. Accepted and intended (silent defaulting hides a mis-deployed secret-style var); the example comment documents setting the variable or removing the line.
- **[Explicit-name never-pass list is incomplete against unknown future secrets]** By construction; mitigation is the category names in the spec plus D4's rule that new secret names are added deliberately, and the operator-override warning that makes an attempted override visible in logs.
- **[`omp` accepted but not launchable until row 9]** Deliberate layering with the spec stating acceptance ≠ availability; the factory's `default:` throw remains the fail-closed boundary. Test suite asserts an `omp` `createAgentConfig()` call throws (no silent partial config).
- **[Shared-file drift with rows 8/9]** Serialized apply order recorded in the proposal's batch table: rows 8/9 extend `AGENT_TYPE_ENV`/never-pass sets and add the factory branch, consuming this change's predicate; re-forking a second supported-type list or credential allowlist is a review blocker.
- **[Mock-only evidence]** Unit tests observe filter/validator decisions over in-memory env maps and real loader code paths; they make no claim about what the official OMP binary does with a credential — real-runtime verification remains user-owned per design §15.
