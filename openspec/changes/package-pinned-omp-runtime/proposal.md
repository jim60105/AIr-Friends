# package-pinned-omp-runtime

## Why

Rows 8/9/12/13/14a/14b/15/17/18 produced the owned OMP settings overlays, the spawn contract, and the FINAL trusted-extension module tree — but none of it exists inside the image: the Containerfile ships only OpenCode, `OMP_TRUSTED_EXTENSION_PATH` resolves only to a development-tree source path, and there is no official `omp` executable, no owned-artifact installation outside agent-writable roots, and no OMP version-health signal. Design §12 ("Official executable and notices") and §14's packaging row require the exact pinned executable + notices with checksum-verified install, the owned tree at row 9's contracted image location, and a warn-only version check following the OpenCode pattern — the last packaging gate before the row-21/22 regression batch.

## What Changes

- **Containerfile — pinned official executable (mirror the OpenCode pattern).** New `omp-unpacker` stage with `ARG OMP_VERSION=18.6.1` plus per-arch `ARG OMP_SHA256_X64` / `OMP_SHA256_ARM64` build args (design §12 table verbatim: `c92a6846d02984e84f07c6362d18add3783f528f494ffcf1e0f26e594f327463` x64, `cb7815330bb117877e4e133562ea82e3001ee470e47393552507b5a7f0407f4a` arm64). Map `TARGETARCH` `amd64→x64`, `arm64→arm64`; anything else fails the build naming the architecture. Download from the exact `v18.6.1` release, verify SHA-256 **before** any install step, fail closed on mismatch. The two executable assets are **allowlisted per architecture, not enumerated by exact filename**: the design table digests `omp-linux-x64`/`omp-linux-arm64`, but the `Containerfile` base image is `denoland/deno:debian` whose unpin-tagged `debian` tag floats the Debian release, so a fully pinned exact filename (e.g. `-glibc`, whose default was glibc at the historical Debian 12 pin) would silently change the libc the runtime runs against every time upstream moves the tag's default — a bigger unpinning than the filename flexibility it buys. The rule is therefore exactly one asset matching `omp-linux-{x64|arm64}[^/]*` for the selected arch, and the digest rule (below) makes silent substitution impossible; the observed asset name is recorded in the stage comment. Install the executable to `/usr/local/bin/omp` **root-owned mode 0755** (`--chown=0:0 --chmod=0755`) — deliberately NOT the existing `$UID:0` 775 pattern: the agent and the app share `$UID` inside the image, so a `$UID`-writable executable would be self-modifiable by the very process the restricted boundary governs (row-12 ownership). No Bun and no speculative runtime dependencies: `deno run` already hosts the application and `omp` is a self-contained binary, so nothing is installed "in case the binary needs it" (design §12).
- **Containerfile — official notices.** Download the release's `LICENSE` (SHA-256 `16c45f9d667442781f03fa198914cc39abcaa48ec5ed8f644643e554ca2fbf63`) and `THIRD-PARTY-NOTICES.txt` (SHA-256 `d0c2e7c05bb4d755044b13fa560be58d01ab7c980b87892400a979397e569a8b`) from the same exact `v18.6.1` release, verify both checksums **before** install, and install both under the image's third-party license location as `/licenses/omp/LICENSE` and `/licenses/omp/THIRD-PARTY-NOTICES.txt` — a new `omp/` subdirectory, because the existing `/licenses/LICENSE` (project license, line 109) is a plain file and a same-name second file at that root cannot coexist with it; the existing project-license COPY is untouched.
- **Containerfile — owned artifacts installed outside agent-writable roots.** A new root-owned image tree `/opt/air/omp/` receives, with pinned `--from=` source paths (the existing image build never passes `--build-context`, so no named-context assumption is introduced): the row-8 owned settings overlays `agent-config/omp/*.yml` → `/opt/air/omp/config/…` (files 0644, dirs 0755, owner root); the row-8 prompt-mapping `SYSTEM.md` artifact → `/opt/air/omp/prompt/SYSTEM.md`; and the FINAL trusted-extension module tree (rows 12→13→14b→17→18 composition, exactly as it exists at row 20's merge point — **content frozen, install-only here**) → the image path that `OMP_TRUSTED_EXTENSION_PATH` resolves to in-image. The module files are root-owned and not writable by the runtime `$UID`.
- **The dev-path → image-path mapping is stated explicitly and lives in `src/utils/omp-paths.ts` (row 9's module; row 20 is the first and only edit-authorized writer of these new exports).** Contract table (single source of truth, exported constants): `OMP_TRUSTED_EXTENSION_PATH` dev value (source-tree module entry under the path rows 12/13/14b/17/18 extended serially) → image `/opt/air/omp/extension/index.ts`; row-8 overlay dev paths `agent-config/omp/restricted.yml`, `agent-config/omp/native-yolo.yml`, `agent-config/omp/models.yml` → `/opt/air/omp/config/<basename>`; the row-8 `SYSTEM.md` prompt-mapping artifact (installed image copy) → `/opt/air/omp/prompt/SYSTEM.md`. The operator-mounted mutable prompt override `/app/prompts/system_prompt_override.md` is NOT relocated — row 8's prompt mapping keeps honoring it when mounted (a mount is operator-owned by design, §12 "preserve existing prompt mounts"); the packaged `/opt/air/omp/prompt/SYSTEM.md` is the image-owned artifact for the default (unmounted) case. Resolution precedence is **image path when it exists on disk, else the dev path** — the factory's row-9 presence-selection and fail-closed absence behavior are consumed unchanged (the `--system-prompt` argument value comes from row 8's mapping resolved through the same image-first helper); development environments (no `/opt/air/omp`) resolve to today's dev paths with zero behavior change.
- **Digest manifest recorded for auditability.** The build computes SHA-256 over every installed owned file (extension tree, settings overlays, prompt artifact) and writes a root-owned, agent-non-writable `PACKAGE-MANIFEST.sha256` beside the installed tree, with one `sha256  <relative-path>` line per file plus a comment recording the reserved-but-unconsumed row-19 6th serial slot (the digest set therefore reflects the 12→13→14b→17→18 composition exactly). **Maintenance invariant (normative):** the digest set is cut only after ALL trusted-extension/settings content has landed; if ANY successor change (rows 21/22 or any later batch/review insertion) lands content touching `/opt/air/omp` inputs, the manifest must be recut in that same change — no consumed-slot drift may pass with a stale manifest.
- **Version health: `src/utils/omp-version.ts` mirroring `verifyOpenCodeVersion` exactly.** Spawn `omp --version` with a 5 s timeout, no network, never an ACP session; injectable detector/logger/command name for mock tests; structured greppable marker `OMP version check: OK|BELOW_MINIMUM|UNKNOWN`; WARN-only on `below_minimum`/`unknown`, never blocks startup, never auto-downloads or upgrades. Image-intended version is exact `18.6.1`; the runtime minimum constant `KNOWN_GOOD_OMP_MIN_VERSION = "18.6.1"` (the runtime check is warn-only per design §12, so a strict-exact constant is safe as the warn threshold and makes any drift visible). Bootstrap calls `verifyOmpVersion()` alongside `verifyOpenCodeVersion()` only when the resolved agent type is `omp`, so plain OpenCode deployments never emit spurious `OMP version check: UNKNOWN` warnings — the one intentional divergence from the OpenCode check's unconditional call, stated here so "follows the same pattern" is not read as "identical call site".
- **New env override `AGENT_OMP_MIN_VERSION`, documented in THIS change across the config trio — treated EXACTLY as `AGENT_OPENCODE_MIN_VERSION` is today.** It is env-only (no `config.yaml` key, no Helm field beyond the existing env map): a commented documentation block beside the OpenCode one in `config.example.yaml` and `helm/values.yaml`, and a commented entry in `.env.example`. This is the config-sync this change owes per the batch contract; no OTHER new config/env/Helm field appears anywhere.
- **Docs:** `docs/OMP_PACKAGING.md` (asset-naming allowlist, digest table, install paths, dev→image mapping, manifest + recut invariant, the explicit statement that image build/execution/arch smoke and installed-binary checks are design §15 USER-owned); Containerfile stage comments mirroring the OpenCode pin comment (bump deliberately, recompute all digests); README small note on the new pin + the fact that runtime enforcement is owned by earlier rows' gates, not by packaging; `AGENTS.md` small note beside the OpenCode pin/check paragraph; CHANGELOG entry; cross-links to `docs/OMP_SETTINGS.md`/`OMP_DISCOVERY.md`/`OMP_NETWORK.md`.
- **Test evidence is mock/unit only** (design §14/§15): Containerfile-parse/unit assertions on assembled ARG values, stage ordering, per-arch allowlist mapping, digest-args-before-install, install paths/ownership, `omp` asset-URL allowlist, no-new-Bun-rule (no `bun` install appears; the pre-existing `denoland/deno` base image is noted, not "proven absent"); image-path resolver assertions (in-image tree sits under `/opt/air/omp`, outside every agent-writable root — never under `/app/data`, `/app/prompts`, or `/home/deno`; dev fallback keeps development behavior); `omp-version` tests on mocked command outputs (OK / low / unknown / timeout / env-override / warn-only-never-throws); manifest fixture assertions; config-trio sync assertions. **No docker builds, no release downloads, no `omp --version` execution.**

## Capabilities

### New Capabilities
- `container-packaging`: Container-image packaging requirements — pinned checksum-verified agent executables and official notices, owned deployment artifacts installed outside agent-writable roots with an auditable digest manifest, and the dev-path → image-path resolution contract.

### Modified Capabilities
- `agent-version-compatibility`: Add OMP bootstrap version-compatibility requirements — the warn-only `omp --version` check with structured `OK|BELOW_MINIMUM|UNKNOWN` markers and the `AGENT_OMP_MIN_VERSION` override — scoped to OMP; the existing OpenCode requirements are not modified.

## Impact

Eventual implementation owns: `Containerfile` (first OMP edits: new `omp-unpacker` stage, final-stage install/owned-tree COPYs; every existing OpenCode section byte-unchanged), `src/utils/omp-version.ts` (new), `src/bootstrap.ts` (one conditional `verifyOmpVersion()` call beside the existing OpenCode one), `src/utils/omp-paths.ts` (image-path constants + image-first resolution; row 9's existing exports and semantics unchanged), `config.example.yaml` / `.env.example` / `helm/values.yaml` (comment-only additions for `AGENT_OMP_MIN_VERSION` beside the existing OpenCode block), `docs/OMP_PACKAGING.md` (new), README/`AGENTS.md` small notes, `CHANGELOG.md` entry, tests `tests/utils/omp-version.test.ts`, `tests/utils/omp-packaging.test.ts` (Containerfile-parse + path/manifest assertions).

Inherited gates, restated without softening: this change installs bytes; it certifies nothing about native enforcement. P0's unresolved verdicts (pre-import exclusion, critical-skill selection, readiness channel, record reset, PARTIAL transport) and row 19's honest no-supported-backend state stand exactly as shipped — a pinned install with warn-only version health is packaging hygiene, not clearance. No mock here proves the installed binary invokes the trusted extension or honors any adapter; design §15 owns those observations. The image build itself (both architectures, checksums against real release assets, startup without an added Bun dependency) is user-owned: this change's own unit suite never builds a container, so the pinned digests are asserted against the design table and the digest pipeline's correctness rests on the recut invariant plus user observation.

- **The OpenCode version bump hinted by row 15's audit note** — explicitly NOT applied here; bumping `OPENCODE_VERSION` is a separate deliberate user decision (its own checksum re-verification contract).
- **Any new config/env/Helm field other than `AGENT_OMP_MIN_VERSION`** — none appears; the pin itself stays a build ARG, mirroring `OPENCODE_VERSION`.
- **Container build/execution/arch smoke and installed-binary checks** — design §15 user-owned acceptance, never this change's tests.
