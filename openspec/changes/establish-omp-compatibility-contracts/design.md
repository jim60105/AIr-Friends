## Context

See `proposal.md` and the approved `docs/superpowers/specs/2026-10-06-omp-integration-design.md`, particularly sections 7–9 and 14–17. Dependencies: none. Existing `acp-integration` describes OpenCode runtime behavior; this change adds compatibility decisions without activating OMP. Official OMP source is pinned to `2a2c6dcbbb558c0f8145f67f28b3370984f2bf60` (`v18.6.1`); the OpenCode LSP audit uses packaging `1.18.21` and resolves its exact source revision; ACP remains SDK `0.14.1`, `terminal:false`.

## Goals / Non-Goals

**Goals:** Produce complete, consumable evidence and data contracts for seven security prerequisites, with an honest blocked outcome when supported native wiring is absent. Source support and deterministic adapter checks are separate evidence columns, neither being a runtime attestation.

**Non-Goals:** No production bootstrap/extension or policy wiring, real process launch, filesystem access cutover, command expansion, model/pool/recovery features, network/search implementation, packaging, or skill recipe changes. No new config/env fields, SDK upgrade, fork, shim or migration. Runtime owners are the later named batch slices; resolving a genuine unsupported interface requires a user decision, not speculative code in P0.

## Decisions

### 1. Bounded evidence ledger, not a speculative native API

The eventual `docs/OMP_COMPATIBILITY.md` ledger contains exactly one row per boundary, and subrows wherever text/binary/search or OpenCode/OMP differ. Each row identifies release/commit, source path and symbol/range, publicly reachable flag/setting/extension entry point, new/load/refresh coverage, consumer, selected mechanism, status (`supported`, `incompatible`, `unresolved`), fixture IDs/results, limitation and user-owned runtime check. `supported` requires a complete source-backed path from official executable or supported trusted-extension entry point to the boundary; an SDK-only/internal method or a partial hook is insufficient. `incompatible` records a disproved selected mechanism, distinguishing that from a claim that every possible alternative is impossible. `unresolved` names the missing link and inspected alternatives. Neither status may be silently upgraded after mock success.

The pure contract module exports the ledger's typed data and `assessCompatibility` result `{ permitted: boolean, blockers: [{ boundary, status, reason, evidence }] }`. It rejects missing/duplicate boundary rows, pin mismatches, incomplete subcases and supported claims without reachable mechanism evidence. It is not called by application startup in this slice; downstream apply review uses its report. There is no generated fake native interface. Documentation and fixtures use the same values rather than introduce a second policy convention.

### 3. Concrete AIr-owned data contracts for downstream consumers

These field names are integration contracts, **not native OMP methods or wire extensions**. Implement only pure completeness/admission validators and source-shaped fixture decoding in P0. Native runtime producers and enforcement stay in their downstream owners.

Readiness authentication must be deliverable through a supported channel with authority independent of model/workspace content. Merely passing a mock boolean `authenticated:true`, or placing a shared secret in model-visible files/env, is not authentication evidence. The contract names the selected credential/channel origin and how a workspace-native tool cannot forge it, never records actual credentials, and never uses the raw Skill API/platform secret. Detailed channel implementation belongs to P5b; absent source-backed channel/identity mapping is a blocker.

Complete destructive target extraction is not implemented as a new patch parser here. Preserve native raw-input fixtures for every enabled edit syntax; record the exact supported parser and complete output or an incompatibility. Downstream must authorize the same operations that execute, including all deletions, move sources/destinations and other patch mutations. Common root/extension authorization remains in P1.

### 4. Fixtures establish consumer decisions, not native support

Use repository Deno unit patterns, immutable native-shaped JSON/YAML/input fixtures with provenance, and the actual pure contract module. No real OMP import/runtime or paid provider is required. Expected outputs are decision objects and recorded attempts, not copied source strings or forwarding call counts alone:

- Complete source-backed ledger passes; missing boundary, SDK-only mechanism, changed pin and supported-without-evidence claims return named blockers.
- Unowned module/factory/plugin/configured-root or dependency-symlink inputs reject before importer spy invocation; owned exact module path is eligible only when an established mechanism covers every route.
- Readiness tuple mismatch, failed authentication provenance, startup error/timeout, stale process/load/registry epoch and chat-crafted acknowledgement reject; a valid supported-channel fixture admits only the matching current identity. A simulated handshake is labeled adapter-only evidence.
- Source-faithful aggregated-overlay fixtures preserve the reset counterexample as an expected incompatibility, including restricted grants and YOLO inherited prompt/deny records. Do not change the modeled merge order to make the approved reset recipe pass.
- Native delete, complete move and complete multi-operation patch fixtures produce every target; missing destination, unknown syntax or a later escaping target produce incomplete/denied result with zero mutation attempts. Raw-input/execution-binding mismatch rejects. Source adapter and completeness validation, not filesystem mutation, are tested.
- Separate mode fixtures reject explicit-only LSP suppression or a global OpenCode clamp affecting YOLO. Cover implicit startup consumers as evidence completeness cases; do not simulate a source path that has not been audited.
- Transport route fixtures reject a partial override covering only text/enrichment while binary/redirect/secondary/search dispatch bypasses it. Established-route mocks record validated per-hop decisions and explicit proxy use, return public text/binary/search results with attribution, reject private targets under enforcing egress and keep provider errors honest. No provider adapter is implemented here.
- Critical-skill collision fixtures select owned canonical paths or reject missing/escaping ownership, including new/load/refresh and two-session resource generation mismatch. Global skill disabling is not a success case.

Use already existing egress/path policy functions wherever these pure fixtures need a policy decision; do not copy a second SSRF classifier or pretend mock import suppression controls the native loader.

### 5. Completion and downstream application gate

P0 completes when the seven-row ledger, real contract validators, native-shaped fixture checks and docs are delivered within the 8-hour budget, **even when the final compatibility verdict is blocked**. Before any downstream application, inspect that verdict: every required boundary/subcase must be supported at the fixed pin under an approved design. Existing selected-strategy incompatibility remains blocking until the user approves a source-backed alternative or an explicit design revision. User acknowledgement is not itself proof of support; update evidence/specs to match an approved decision before resuming. Further proposal drafting is permitted, implementation is not.

No release/pin/settings claim is changed automatically. No application wiring or config synchronization is deferred from this slice, because none is introduced here. Docs describe static findings, actual unit/mock outcomes, and all real runtime checks as user-owned/unverified. The applicable local contract/unit/type verification is included in the 0.5-hour allocation; live `omp --version`, agents, providers, platforms, containers and bwrap remain excluded.

## Risks / Trade-offs

- **Known approved-design conflict:** Reset-then-mode overlays do not act as independent merge barriers in inspected source. Keep the approved design unchanged; document/report the conflict and block affected application rather than fabricate compatibility.
- **Breadth versus depth:** Seven boundaries fit only because this is a bounded audit/contract change, not runtime work. Three audit hours trace named entry points/direct consumers; unresolved links remain explicit blockers. Additional research needs a user-approved split, not silent scope growth.
- **False assurance:** Pure validators and fixtures verify their consumers, not actual executable hook coverage. Even supported source paths require the section-15 user runtime checklist.
- **Shared state:** Native process-global skill/LSP/resource state may complicate pooled ownership. The ledger must cover it or remain unresolved; P0 cannot hand-wave it away with per-session mock storage.
- **Conflicts:** `acp-integration` receives additive compatibility requirements, `CHANGELOG.md` is shared, and later slices consume the contract module. Apply serially under a single integration owner; no downstream field changes without updating fixture/docs consumers.

## Workday and Dependency Summary

No predecessors. Budget: 3h audit + 1.25h typed contract/ledger + 1.5h unit/mock checks + 0.75h docs/changelog + 0.5h verification + 1h contingency = **8h maximum**.
