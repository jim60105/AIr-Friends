## Goals / Non-Goals

**Goals:** OMP admits the deployment-resolved shared root for owned-skill instruction reads and script execution at every enforcement layer; the declared root is parameterized rather than asserted, with the carrier of the declaration made explicit; the generated declaration cannot out-rank an authored pin and is refreshed at every spawn; the extension obtains the root from a deployment-owned source that the child cannot rewrite; every retained denial behavior is unchanged and tested.

**Non-Goals:** reducing identity, containment, link or generation verification; changing the interpreter allowlist, the `scripts/*.ts`-only enumeration or the YOLO short-circuit; adding a second tree, an ownership-exemption flag or a per-agent root; the packaging collapse; changing the extension bundle contract, its manifest scope or its module-ownership evidence.

## Accepted Security-Posture Change

This change deliberately relaxes OMP's ownership and immutability posture, and the user accepted that consequence. Concretely: the skill tree the deployment resolves is no longer required to be root-owned, agent-non-writable or non-group/world-writable, so the runtime user that runs the agent can modify ordinary skill content the same deployment later reads and executes.

Three compensating invariants bound that acceptance, and each is stated once here:

1. The auto-approve inventory is constructed ONCE per connector or session, so a script created later in that connector's or session's lifetime is never enumerated and never approved (tested by `Inventory Denial Invariants Survive The Ownership Relaxation` → `Script planted after inventory construction is not approved`). This bounds within one construction; a script planted before the next construction is enumerated by that construction — the exposure is the accepted posture and is not claimed to be bounded across constructions.
2. Decision-time re-verification of `(dev, ino, ctime, size)` for both the root and the script stays, so in-place modification of an enumerated script denies (tested by the same requirement → `In-place modification of an enumerated script is denied`).
3. The interpreter allowlist stays `deno` only and enumeration stays `scripts/*.ts` only, so non-Deno external scripts remain unusable on both agents (tested by `Skill Auto-Approve List Construction Over The Single Resolved Root` → `Non-TypeScript script remains non-executable on either agent type`, delivered by `unify-skill-root-and-inventory`).

Three further controls belong to the same acceptance rather than to the trio: critical minting keeps consulting the root's observed read-only determination, so a writable tree mints no critical authority (`Pinned critical layout keeps its ownership requirement`); the generated declaration is validated against the daemon's own resolved root and is placed so it cannot out-rank an authored pin (`The declared skill directory follows the resolved root`, `Overlay ordering and environment posture are spawn-change contracts`); and that declaration's one writable path is explicit in the placement contract (`Workspace layer cannot loosen the pins`).

## Decisions

### D1. Drop the ownership clauses at all three layers, keep every identity clause, and keep the read-only fact load-bearing where it still is

Remove the `uid === 0`/`0o222` owner-writable test and the `0o022` group/world-writable test (and their error reasons) in `src/acp/omp/owned-skills.ts`, in `src/acp/omp/extension/read-replacement.ts` at the root, the target and each component, and in the daemon's `src/acp/filesystem-roots.ts` observation. Retained unchanged everywhere: absolute canonical path, link-free every component, real directory or file, `nlink === 1` for files, realpath containment, the supplied `dev`/`ino` identity, the writable-root overlap check and the current-generation requirement.

The ownership-and-mode observation stays in exactly one place because it is load-bearing there: `src/acp/omp/owned-skills.ts:174-175` currently hard-codes `isReadOnlyRoot: true`, and `evaluateCriticalSkillSelection` mints critical authority only when it is true. The producer SHALL derive that flag from the observed root's own ownership and mode (the clauses removed elsewhere, evaluated on the root alone), and a candidate whose relative path matches a pinned critical identifier's `SKILL.md` layout SHALL be refused when the flag is false. Ordinary skill admission never consults the flag, so the relaxation is unaffected everywhere else, and the carve-out changes no shipped behavior because the pinned layout is unpopulated.

Alternatives rejected: keeping the group/world-writable refusal (the shipped tree is `775`, so the requirement would still fail); making the tree root-owned instead (the operator configures the root and the packaging change removes the root-owned tree, so ownership cannot be a precondition); an "allow-agent-writable" opt-in flag (a second posture to reason about for no added safety); dropping the clauses in only one layer (the extension and the daemon callback both observe the root, and missing either leaves the shared root unusable).

### D2. Parameterize the declared root end to end and state which document carries it

`ompSettingsSourcePlan` SHALL require exactly the caller-supplied resolved root plus the generated declaration's path, `assertOwnedSettingsDocument` SHALL take `expectedSkillRoots` from its caller, and both composed mode documents SHALL render the parameterized root instead of the literal. `src/acp/agent-factory.ts` passes the root it already observed for the selected agent at both call sites, so the declared root and the resolved root cannot disagree.

The assertion is re-scoped to the carrier. Today every resolved overlay must declare `skills.customDirectories` exactly (`src/acp/omp-settings.ts:1184-1194`, called for each resolved overlay at `src/acp/agent-factory.ts:373-388` and in-child at `src/acp/omp/extension/critical-skills.ts:74`), which is impossible once the authored documents stop declaring it. After this change: the generated declaration SHALL declare exactly the resolved root; each authored mode document SHALL be validated for its registered pins and for the absence of a skill directory; the composed fold carries exactly the resolved root by construction; and the in-child image-document check validates the registered shape and takes the root from the launch environment (D4). A drifted hard-coded directory in an authored document is therefore a validation failure, which is stricter than today's blanket per-file requirement rather than weaker.

### D3. Generate a minimal declaration, place it outside the owned tree, and never let it out-rank a pin

The authored mode documents stop hard-coding a skill directory (they keep `skills.enabled: true` and the seven foreign-source toggles `false`). Each mode's generated declaration contains exactly one key — `skills.customDirectories` with exactly the resolved root — so the composed fold inherits enablement and every other pin from the authored document and carries the resolved directory unambiguously. The fold basis is `docs/OMP_SETTINGS.md:56-62` (all CLI overlay files fold into one aggregated mapping; `#deepMerge` retains base-only entries), which is exactly what a first-position declaration relies on.

The declaration lives at `{baseRoot}/omp-overlays/{mode}-skill-root.yml` — a deployment-owned directory under the same base root the process state uses, deliberately OUTSIDE `plan.agentDir` and `plan.ownedHome`, which the pre-native-request overlay observer rejects (`src/acp/omp/settings-sources.ts:290-301`). Since the file must be daemon-writable at spawn time, it is the one path exempt from the authored-overlay placement rule, and it is otherwise checked exactly like every other overlay: link, regular-file and canonical-parent checks plus the accepted size/mtime identity, which then reveals any post-spawn rewrite of the declaration rather than exempting it (`:310-320`). The observer keeps its metadata-only contract and gains no content read; the declaration's parsed content is validated against the resolved root at spawn time by the factory, which just wrote the file. The write is symlink-refusing (`lstat`, then a create that fails on an existing link) and unconditional, so no pooled directory persists a stale or rewritten declaration, and the declaration is passed FIRST among the `--config` overlays while the authored mode document stays LAST.

Alternatives rejected: putting the whole composed document in the generated file (a rewrite of a writable file would then be able to loosen the approval-mode, LSP and provider pins); passing the declaration last (a rewrite could out-rank those pins); placing it inside the mode-scoped agent directory (the placement observer refuses exactly that, so every session would fail closed); relying on array/value merge without generating anything (the authored document would have to hard-code the operator's root, which it cannot); inspecting and skipping an already-correct file (a stale or tampered file would survive for the whole pool lifetime).

### D4. The extension takes the root from its deployment-owned launch environment

`observeDeclaredSkillRoots` stops reading the image document's hard-coded directory and stops importing the constant. The daemon adds the resolved root to the settings-source plan's expected environment set, where `finalizeOmpSpawnEnvironment` assigns and then verifies it alongside `PI_CODING_AGENT_DIR` and the other owned values on both routes; the extension reads that value from its launch environment (it already reads the launch environment and derives owned roots from it), treats it as its only witness of the declared root, and verifies it is one absolute, existing, non-link directory its own root observation accepts, otherwise denying with the existing frozen-empty posture and no fallback. An environment value is fixed at spawn and consumed at load time, so unlike a writable file the child cannot rewrite its own authorization source, and the per-spawn and pooled shapes behave identically — which the current file-based path cannot guarantee, since the two shapes have different writable base roots (`src/acp/agent-factory.ts:320-322`). The image mode document remains the source of every other pin and is still parsed and validated for its registered keys. The skill-URI wiring is restricted-launch scope, which the tasks state explicitly.

### D5. Retained denial behavior

The relaxation changes only which roots are admitted, never how a script is approved: one inventory per connector/session, decision-time entrypoint and identity rechecks, `deno`-only interpreter anchoring, `scripts/*.ts`-only enumeration, the unchanged YOLO short-circuit, and the root-exact callback classification. The invariants and controls in the posture section are the contract for that; invariant 3's mechanism is owned by the co-released `unify-skill-root-and-inventory`.

### D6. Ordering

This change validates against `unify-skill-root-and-inventory` (it admits and parameterizes the root that change resolves), and that change cannot be released without this one (OMP would resolve the shared root and then refuse it). `collapse-skill-packaging-to-one-tree` follows both, because removing `/opt/air/skills` is only safe once no code path selects, declares or trusts it.

## Risks / Trade-offs

- **The agent can modify ordinary skill content it is later trusted to read and execute** → accepted (stated once above); a modification after construction denies and a script added after construction is never approved by that inventory. A script planted before the next construction is enumerated by it, so the bound is per construction, not permanent.
- **Critical-skill immutability** → the observed read-only flag in D1 keeps critical minting gated on the root's ownership and mode, so a planted pinned layout in a writable tree mints nothing; the shipped image already mints zero critical references because the layout is unpopulated.
- **The declaration is writable and shares a directory with the mode-scoped state** → the daemon's write contains one key; the file itself could carry anything, so the bound is that the authored mode document is last and is root-owned read-only, that the declaration is rewritten at every spawn, and that one process lives per mode-scoped state root, so no other pin can be loosened and no script or critical authority derives from it.
- **The overlay placement contract gains one exception** → recorded explicitly in the modified settings requirement and in the observer task, with the compensating checks named; the alternative (a non-writable declaration) is impossible for a runtime-resolved value.
- **The extension trusts the daemon's spawn environment** → the value is fixed at spawn and verified by the existing environment finalization, which is strictly stronger than a writable declaration file; an absent or unacceptable value denies with zero skill authority.
- **The digest manifest covers both the changed overlays and the changed extension closure** → recut over a simulated owned root in this change, per the repository's recut invariant.
- **Test churn**: suites assert the three ownership layers and the constant → rewritten in the groups that own each behavior.

## Migration Plan

No data migration and no operator action: the deployment's configured root stays where it is and now works for OMP. Deploy in one release with `unify-skill-root-and-inventory`; roll back by reverting both, since the image tree still exists until the packaging change. `collapse-skill-packaging-to-one-tree` must not be applied before this change.
