## Context

See `proposal.md` — Why. Constraints that shape the approach: the approved design §5/§7/§12; the P0 change's recorded verdicts (the reset-then-mode overlay strategy is incompatible as stated); row 7's supported credential set and supported-type predicate; and the pinned official sources `v18.6.1` / `2a2c6dcbbb558c0f8145f67f28b3370984f2bf60` for every schema key, env var, header and prompt mechanism cited below. OpenCode's current equivalents live in `agent-config/opencode.json` (`provider.gemini`/`openrouter` with `X-Title: AIr-Friends`/`HTTP-Referer`, `autoupdate: false`, `compaction: {auto, prune}`, `agent.*.prompt: {file:/app/prompts/system_prompt_override.md}`). This change authors settings **content and assembly data**; rows 9/14/15/20 own launch, enforcement, implementation, and installation.

## Goals / Non-Goals

**Goals:** One pure composition module that deterministically produces restricted and native-yolo settings content; a machine-checkable allow-list of the pinned registered schema keys the overlays may touch; faithful modeling of the pinned merge semantics so the surviving-lower-record behavior is tested and gated rather than papered over; source-backed provider-identity and prompt mappings with their limits stated; consumer-visible unit tests for every decision in `proposal.md`.

**Non-Goals:** No subprocess launch, argument assembly, `PI_CODING_AGENT_DIR` assignment, pool identity, `tools.approval` record content, LSP implicit-startup implementation, settings-file checksum/install, executable packaging, native runtime execution, or live-provider checks. No new `config.yaml`/`.env`/Helm field. No edit of P0 artifacts, row-7 files, or the approved design.

## Decisions

### 1. Composition module + deployment-owned asset files, not inline strings

`src/acp/omp-settings.ts` exports the typed composition: `ompSettingsForMode(mode: "restricted" | "native-yolo")` returning `{ overlayFiles: { path, content }[], modelsYamlContent, systemPromptSourcePath, providerEnvKeys, envPosture }`, backed by real asset files `agent-config/omp/restricted.yml`, `agent-config/omp/native-yolo.yml`, `agent-config/omp/models.yml` authored in this change. Rationale: row 20 must checksum/install the files (design §12 "package owned settings … outside agent-writable roots"), and row 9 passes the paths; tests assert parsed content, mirroring the existing `agent-config/opencode.json` asset pattern rather than a second convention. Alternative considered — generating YAML from code only — rejected because packaging/checksums and operator review need real files; alternative — one shared base file plus a delta file — rejected because design §12 requires shared content to be deployment concerns and arrays (`disabledProviders`) replace wholesale, so a base+delta chain multiplies precedence surprises; each mode file is complete and self-contained, and the shared subset is enforced by the non-contamination test instead of file composition.

### 2. Precedence comes from deployment ownership, not from more overlay files

Pinned precedence: `built-in defaults < global config.yml < project <cwd>/.omp/ < --config overlays < runtime overrides < setting env var` (`docs/settings.md`), and `#readConfigOverlays` folds all CLI files into one mapping before merging over the lower layers (`packages/coding-agent/src/config/settings.ts:2425-2433, 3827-3831`). Consequences encoded as contracts for row 9:

- Ordered `--config` overlays: shared-first, mode-file LAST (`PI_CONFIG_FILES` env overlays load *before* `--config`, so it stays deployment-owned and un-set by workspace content; it must never be exported into an OMP subprocess).
- The hostile *project* layer is removed at the root: native project settings are discovered ONLY from the process working directory's `.omp/` and never by ancestor walk-up (`docs/settings.md`, "Native project settings are intentionally scoped to the process working directory's `.omp/`"). Row 9's neutral deployment-owned launch cwd therefore prevents workspace `.omp/config.yml` from ever entering the merge. This is a source-backed mitigation, not this change's implementation.
- The *global* layer must be an empty deployment-owned agent dir: `PI_CODING_AGENT_DIR` under the selected process state root (design §5; env wiring is row 9). A pre-populated or workspace-writable global file is a hostile layer.
- The overlay files must live outside agent-writable roots (row 20) because a live file watcher reloads overlays and a live-reloaded project/overlay edit can re-open inherited records (design §7).

Alternative rejected: relying on overlay ordering alone to "beat" hostile project/global content — ordering wins same-key conflicts only; `#deepMerge` (`settings.ts:3850-3869`) keeps keys present only in lower layers.

### 3. Restricted pins: exactly these registered keys, validated at assembly

The restricted overlay pins, each registered at the pinned revision (source of the exact id):

Design §5 requires a pinned non-YOLO mode, never an implicit default. |
| `lsp.enabled` | `false` | `docs/settings.md` §Shell/eval/LSP (`lsp.enabled`, default `true`) | Pin only. Row 15 owns the full restricted LSP disablement (implicit/cold-start paths, tool availability) and must not regress this pin. |
| `startup.checkUpdate` | `false` | `packages/coding-agent/src/modes/settings.ts:1028` (`cfgStartupCheckUpdate`, default `true`), consumed by `checkForNewVersion()` (`main.ts:233-244`) | No startup version probe/notification. |

The same four update posture keys plus compaction (§5) and provider posture (§4) are shared deployment content present in BOTH overlays. The validator (`assertOwnedSettingsDocument`) rejects any key not registered at the pinned revision and any value outside the registered enum/type — unknown YAML keys and invalid values silently falling back to schema defaults are explicitly *not* protection (design §7) — and rejects restricted-only keys appearing in the YOLO document (§6). Keys deliberately NOT pinned here: `tools.approval` (row 14 policy records), `mcp.enableProjectConfig`, `skills.*`, `bash.enabled`, `eval.py/js`, `async.enabled`, `fetch.enabled`, `web_search.enabled`, `computer.enabled`, `tools.xdev` — these are enablement-surface choices owned by the row-14 tool-inventory policy (and rows 17–19 keep fetch/search parity), so this change must not pre-empt them; the table above is the complete settings-layer pin set for this slice.

Alternative considered: pinning `tools.approvalMode: always-ask` — rejected: design §6 requires the ordinary write/edit capability to reach the existing write sink/policy, and `always-ask` would prompt every workspace write, shrinking parity with no security gain the row-14 gate does not already provide.

### 4. Provider/application identity via provider ids, env credentials, and `models.yml` headers — with one honest non-preservation

- Gemini: OMP's provider id is `google` and its credential variable is `GEMINI_API_KEY` (`docs/providers.md` core-provider table). No settings key is needed; `GOOGLE_GENERATIVE_AI_API_KEY`, which the OpenCode factory sets, is NOT passed for OMP (already enforced by row 7's never-pass set).
- OpenRouter: credential `OPENROUTER_API_KEY`; owned `agent-config/omp/models.yml` adds provider-level `headers: { X-Title: AIr-Friends }`. Source basis: custom-provider and model `headers` are real schema fields (`docs/models.md`), applied as `let headers = { ...model.headers }` in the shared OpenAI request setup (`packages/ai/src/providers/openai-shared.ts:228`), and pinned OMP never writes an `X-Title` key, so the owned value survives on OpenRouter requests.
- **HTTP-Referer is recorded as NOT preservable through the supported content path**: for provider `openrouter` the setup runs `Object.assign(headers, getOpenRouterHeaders())` (`openai-shared.ts:229-231`), and `getOpenRouterHeaders()` (`packages/ai/src/utils/openrouter-headers.ts`) hard-codes `HTTP-Referer: https://omp.sh/` and `X-OpenRouter-Title: omp` over model/config headers. Only an internal `prependHeaders` hook (hard-wired per provider) or an extension-level transport rewrite could override it, and neither is a supported content mechanism here. The change therefore (a) keeps `X-Title: AIr-Friends` as the carried application identity, (b) documents the HTTP-Referer divergence in `docs/OMP_SETTINGS.md`, and (c) files it as a P0-style compatibility item (`packages/ai/src/providers/inference-headers.ts` shows the same built-in-identity pattern) rather than inventing an env/settings key or using a mock to fake preservation. `OMP_APP_NAME` (`packages/utils/src/dirs.ts:getAppName`) is broker usage-attribution only and is explicitly not the header mechanism.
- Model IDs: owned assets contain zero hardcoded model ids. Operator model selectors flow through the existing row-7 config surfaces and row 6's stable-first advertised-catalog selection; a catalog miss is an error, and OpenCode ids (`openrouter/...` in `agent-config/opencode.json`) are never translated into OMP assets (design §10/§12). Alternative rejected: vendoring a model list into `models.yml` — it would freeze an advertised catalog and violate "do not hardcode OpenCode model IDs".

### 5. Compaction stays enabled; native differences are documented, not harmonized

Both overlays carry `compaction.enabled: true` (registered `compaction.enabled`, default `true`) and rely on the pinned native strategy (`compaction.methodOrder` default `remote, snapcompact, handoff, shake, soft`, `asyncEnabled`, `midTurnEnabled`, `thresholdPercent`/`thresholdTokens` defaults) without pinning tuning values. OpenCode's `{auto: true, prune: true}` has no OMP equivalent: OMP's history reduction is method-ordered summarization, and there is no registered `prune` key — inventing one (or claiming algorithmic equivalence) is prohibited; `docs/OMP_SETTINGS.md` carries the difference table. Alternative considered: pinning `methodOrder`/thresholds to mimic OpenCode behavior — rejected: unverifiable behavioral emulation, and any such tuning change would need its own approved contract.

### 6. Update posture: disable the automatic surfaces that have schema support; version change stays deliberate

Design §12 requires disabling "executable self-update and unintended update behavior". The pinned schema's honest coverage is `startup.checkUpdate: false` (no startup version probe/notification) + `marketplace.autoUpdate: off` + `update.channel: stable`. The actual binary replacement is the explicit `omp update` command (`packages/coding-agent/src/cli/update-cli.ts`), which no settings key disables — so the "no unintended update" posture is completed by deployment facts stated in docs: the image installs `/usr/local/bin/omp` from the exact pinned release with checksums (row 20, design §12), and version changes happen only through deliberate image rebuilds. `DENO_NO_UPDATE_CHECK` (already in the row-7 base allowlist) is noted as unrelated to OMP's updater. No `update.enabled`-style key is invented; the docs record that the explicit command remains operator-accessible.

### 7. Prompt mapping: explicit custom-prompt route, application asserted only after P0 verification

Source-backed mechanism (`docs/system-prompt-customization.md`): `--system-prompt <text-or-file>` replaces the default instruction block with the literal file route while OMP's generated footer (project context, completion requirements), skills, and rules survive; discovered `SYSTEM.md` under the active agent dir is the same route without a flag, and the agent-dir lookup honors `PI_CODING_AGENT_DIR`. Mapping declared here: `/app/prompts/system_prompt_override.md` is installed (row 20) as `<owned agent dir>/SYSTEM.md` AND exposed as the explicit `--system-prompt` target row 9 may pass (explicit wins over discovered). The per-file mounts (`prompts/system_self_research.md`, `system_memory_maintenance.md`, `system_spontaneous.md`, retry/reminder text) are AIr-rendered payload prompts consumed by the existing prompt-template pipeline, not agent system prompts, and need no OMP settings translation — the docs state this. Honest limit: `customSystemPrompt`/`--system-prompt` semantics (skills/rules/footer retained, default tool inventory/tool-policy guidance absent) mean the override file is interpreted as custom instruction text, not a verbatim OpenCode `agent.*.prompt` swap; whether the current override text remains behaviorally adequate under OMP's generated surfaces is a P0-runtime/user-verification item, and this change asserts only the mapping, not runtime application. Rejected alternatives: `SYSTEM_TEMPLATE.md` (Handlebars — the override file is not a template) and full programmatic `CreateAgentSessionOptions.systemPrompt` replacement (SDK-only, unreachable from the official ACP launch, and would drop the generated footer).

### 8. Mode non-contamination is structural

The composition module builds each mode document from disjoint constant key sets — `RESTRICTED_ONLY_KEYS = {tools.approvalMode(write), lsp.enabled(false), disabledProviders(...)}` and `NATIVE_YOLO_KEYS = {tools.approvalMode(yolo)}` — plus the shared deployment set; there is no code path that copies restricted content into the YOLO document, and the unit test asserts the YOLO document contains no `tools.approval*`, no `lsp.*` key at all, and no `disabledProviders` entry, while the restricted document contains the §3 pins (design D6/D7: native YOLO is maximally permissive; sandbox/egress and the ACP-client-side containment still apply per design §5, and neither is a settings key). A shared `--config` base file is rejected (§1) precisely because array-replacement and deep-merge make partial sharing subtle.

### 9. The record-reset gate is modeled faithfully and stays open

The composition exposes `recordResetGate = { status: "unresolved", strategy: "reset-then-mode-null", reason, residualEvidence }`, and the test suite models the pinned merge exactly as P0 does: fold `reset.yml` (`tools.approval: null`) + mode mapping into one mapping, `#deepMerge` over lower `{tools.approval:{unknown_tool:"allow", read:"deny"}}`, assert the surviving `unknown_tool:"allow"` (restricted) and surviving lower `prompt`/`deny` (YOLO) as the EXPECTED result, and reject any assertion that the recipe clears records. The test never reorders layers to make a reset pass (P0's fixture rule). Candidate alternatives recorded for P0 verification, neither certified: (a) hostile-layer removal — empty deployment-owned global agent dir plus deployment-owned launch cwd so project/global layers hold nothing (`docs/settings.md` cwd-scoped project discovery), making "surviving lower records" empty in practice; (b) programmatic `Settings.isolated` overrides, which are SDK-internal and therefore not a supported official-binary mechanism; (c) `task.agentCompactionThresholdOverrides`-style explicit `null`-clearing semantics, which exist only for that one record key and do not generalize. Until P0 records a supported mechanism and the user approves, the requirement and docs state plainly: the restricted runtime default-deny (row 14) is the operative boundary; settings-layer clearing is not available, and lower-layer grants must be assumed present at spawn.

## Risks / Trade-offs

- **Gate misread as support** → the gate ships as a named data value plus an explicit surviving-record test; docs repeat that no mock certifies native enforcement, and row 22's checklist keeps the runtime item user-owned.
- **`disabledProviders` incompleteness** (catalog namespace is large) → validator requires an explicit complete array plus a doc-listed enumeration reviewed against pinned `omp config list`/catalog KDL during implementation; a wrong entry surfaces as a provider-unavailability error at first live use, not a silent widening.
- **Schema drift across future pins** → validator keys embed the pin string; changing `OMP_VERSION` forces the key audit to fail loudly rather than silently accept stale keys.
- **Prompt-override behavioral divergence** → mapping only; runtime adequacy is user-verified; the override file itself is untouched by this change.
- **HTTP-Referer identity loss accepted** → recorded incompatibility with exact source symbols; escalating it is the user's design decision (batch rule), not this slice's.
- **Shared files (factory/asset tree/CHANGELOG)** → single integration owner applies serially; this change is consume-only against `agent-factory.ts`.

## Migration Plan

Data-only change: new asset files + module + docs/tests; nothing at runtime reads them until row 9 wires them, so deployment is inert until successors land. Rollback is reverting the commit; no config migration, no state, no compatibility shim.
