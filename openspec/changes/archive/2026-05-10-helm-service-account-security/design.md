## Context

Kubernetes automatically mounts a ServiceAccount token into every Pod unless explicitly disabled. AIr-Friends communicates only with Discord/Misskey APIs and spawns local subprocess agents — it never calls the Kubernetes API. The projected token therefore provides zero benefit while creating unnecessary credential exposure if the container is compromised.

The Helm chart currently has no `serviceAccount` section in `values.yaml` and no `automountServiceAccountToken` field in the Deployment template. This means every deployed Pod implicitly uses the `default` ServiceAccount with token automounting governed by whatever `automountServiceAccountToken` is set on that SA — which is cluster-operator-controlled and not guaranteed to be `false`. Relying on cluster defaults is fragile; the only reliable approach is to set the field explicitly at the Pod spec level.

The standard Helm scaffold pattern (as generated by `helm create`) includes a `serviceAccount` values block with `create`, `annotations`, `name`, and `automount` fields plus a conditional ServiceAccount template. Adopting this well-known pattern keeps the chart idiomatic and familiar to operators.

## Goals / Non-Goals

**Goals:**
- Default `serviceAccount.create: false` — do not create a dedicated ServiceAccount unless the user asks
- Default `serviceAccount.automount: false` — set `automountServiceAccountToken: false` at the Pod spec level regardless of whether a dedicated SA exists
- Provide a conditional ServiceAccount template for users who want a dedicated SA (e.g., to attach IRSA annotations for AWS or Workload Identity for GCP)
- Keep values schema consistent with the standard `helm create` scaffold for operator familiarity

**Non-Goals:**
- Adding RBAC Role/ClusterRole resources — the app still doesn't need Kubernetes API access
- Removing the ability for users to opt in to token mounting if they have a custom use-case
- Changing application code

## Decisions

### Decision: Pod-level `automountServiceAccountToken: false` over SA-level only

**Choice**: Set `automountServiceAccountToken: false` on the Pod spec (`deployment.yaml`), gated by `serviceAccount.automount`.

**Rationale**: Pod-level setting overrides the SA-level setting. If `serviceAccount.create: false`, the Pod uses the `default` SA (which may have `automountServiceAccountToken: true` at the cluster level). Setting it at Pod level is the only reliable way to ensure tokens are not mounted regardless of what SA is used.

**Alternative considered**: Only set it on the ServiceAccount resource. Rejected because when `serviceAccount.create: false` the SA is not ours to control.

### Decision: Follow standard `helm create` scaffold for values schema

**Choice**: Use `serviceAccount.create`, `serviceAccount.annotations`, `serviceAccount.name`, and `serviceAccount.automount` keys — identical to the Helm scaffold.

**Rationale**: Operators familiar with standard Helm charts will immediately understand the knobs. No need to invent a different schema.

### Decision: `_helpers.tpl` helper for `serviceAccountName`

**Choice**: Add `air-friends.serviceAccountName` helper that returns `serviceAccount.name` when `serviceAccount.create: false`, or the full chart name when `create: true` and `name` is empty.

**Rationale**: Consistent with standard Helm pattern; keeps the template clean.

## Risks / Trade-offs

- **[Risk] Existing deployments that rely on default SA token** → Mitigation: The default SA token is normally unused by the app; the change is additive. Operators who genuinely need SA access can set `serviceAccount.automount: true`.
- **[Risk] Cluster-level `automountServiceAccountToken: false` on default SA** → Mitigation: Pod-level field explicitly governs behaviour; no conflict.
- **[Trade-off] Extra values block** → Adds ~5 lines to `values.yaml`; negligible complexity, high security value.

## Migration Plan

Pure Helm chart change — no application restarts caused by logic change, only by the Pod spec patch. On `helm upgrade`, the Deployment is updated with the new `automountServiceAccountToken: false` field; Kubernetes performs a rolling update (Recreate strategy is already configured, so the old Pod is terminated before the new one starts). No data migration needed.

Rollback: `helm rollback <release> <revision>` restores the previous Deployment spec.
