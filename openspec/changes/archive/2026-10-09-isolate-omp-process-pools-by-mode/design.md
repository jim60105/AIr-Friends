## Context

`AgentProcessPool` (`src/core/agent-process-pool.ts`) keys its `entries: Map<string, PoolEntry>` by the canonical `poolKey` string from `PoolRunOptions`, lazily spawning via `acquireProcess(poolKey, connectorOptions)` and creating per-key directories in `ensureSharedDirs(poolKey)` (`channel-cwd`/`channel-tmp`/`opencode-data` under the bot data root). The orchestrator (`src/core/session-orchestrator.ts`) currently resolves effective YOLO mid-flow: `processMessageInternal` computes `yoloDecision` early (before context assembly), and it precedes `createAgentConfig`/`processPool.run` — but the scheduler sessions (`processSelfResearch`, `processMemoryMaintenance`, `processChannelMemoryMaintenance`) simply pass `this.yolo` (the global flag) at every call site, and `processChannelMemoryMaintenance` has no per-session resolution at all. Row 9 shipped the factory `omp` branch whose mode-scoped state roots (`src/utils/omp-paths.ts`: `ompAgentDir`, `ompProcessTmpDir`, `ompLaunchCwd`, `ompXdgDataHome`) are mode-distinct **independently of pool-key composition**. Row 6 landed the connector's `setSessionModel`/`setReasoningEffort`/config-option cache/reconnect config restoration — consumed here unchanged. Design §5 ("Pool identity and state") and §10 step 1 turn this into the contract: mode in OMP pool identity, resolution before acquisition everywhere, lease preserved, OpenCode untouched.

## Goals / Non-Goals

**Goals:** OMP entry identity = pool key + resolved mode with same-mode reuse and cross-mode separation (dual-mode channel coexistence); explicit mode/agent-type fields on `PoolRunOptions` with the pool never inferring either; effective-mode resolution before acquisition at all enumerated entry points (pool and per-spawn paths); the global lease serializing across mode-split entries; OpenCode pool identity/environment byte-identity; per-spawn mode threading with `SKILL_SHARED_PROCESS=1`/no-frozen-`SESSION_ID` asserted; ownership bookkeeping (original mode + state namespace) written at acquisition as row 11's durable read target; consumer-visible tests for every claim.

**Non-Goals:** Reconnect/same-mode `session/load` verification and gate-context restoration (row 11); readiness gating before prompt (row 13); tool policy (row 14); LSP (row 15); staging prompt text / payload portability (row 16); fetch transport (row 17); web search (row 18); code search (row 19); packaging (row 20); any edit of P0/row-6/row-7/row-8/row-9 artifacts or contracts; the YOLO decision rules themselves (unchanged); dashboard chat sessions (own connector lifecycle, never the pool — unchanged); OpenCode directory layout; any new config/env/Helm field.

## Decisions

### 1. Mode is an explicit `PoolRunOptions` field; the pool composes entry identity

`PoolRunOptions` gains `agentType: AgentType` and `permissionMode: "restricted" | "native-yolo"` (naming: the two spawn modes row 9 defined; `permissionMode` derives mechanically from the already-resolved `yolo` boolean at each call site — no second resolution anywhere). The pool composes the **entry key** as `poolKey` verbatim for OpenCode and `poolKey + ":" + permissionMode` (a `modeKey()` helper, restricted/native-yolo segment, mirroring row 9's state-namespace segment naming so pool identity and state namespace read alike) for `omp`. `PoolEntry` records both, `acquireProcess`/`scheduleReclaim`/`ensureSharedDirs` operate on the entry key, and `ensureSharedDirs` creates the entry key's directories (OMP: the mode-segmented roots the factory's env values already point at — the pool's job is only to `mkdir` what the factory exports, byte-identically, same rule as the existing resolved-path contract). Rationale: keeping `poolKey` canonical (spec keeps every OpenCode scenario verbatim) while the entry identity gains one dimension only for OMP. Alternatives rejected: (a) restamping an existing entry's mode (recreates the mixed-mode process D6/D7 prohibit); (b) folding mode into every call site's `poolKey` string (leaks pool internals into six orchestrator call sites and changes OpenCode-adjacent key strings needlessly).

### 2. Row 9's factory-side distinctness stays; pool identity is additive

Row 9's `omp-paths` mode segment remains in every state root even though the pool key now also carries mode — defense-in-depth, and the row-9 proposal explicitly warns row 10 MUST NOT weaken it. `agent-factory.ts` is NOT edited: its `yolo` argument is exactly the resolved mode, and this change's tests assert the value passed at every call site is the resolved decision. The pool records the state namespace for ownership bookkeeping by reading the factory-produced env (`agentConfig.env` `TMPDIR`/`PI_CODING_AGENT_DIR` for OMP; `XDG_DATA_HOME`/pool-key data root for OpenCode) rather than recomputing a second namespace formula — one source of truth (`omp-paths.ts` via the factory), no drift.

### 3. Resolution ordering per entry point: hoist, don't re-resolve

Message/lurk already resolve `getEffectiveYolo` before acquisition — a test-pinned ordering, not a code change. The scheduler paths (`processSelfResearch`, `processMemoryMaintenance`, `processChannelMemoryMaintenance`) keep passing the global-flag value (`this.yolo`) — their existing decision rule — but every call site is reordered so the resolution statement precedes `createAgentConfig`/`createConnector`/`processPool.run` textually and structurally (an explicit `const permissionMode = resolvePermissionMode(this.yolo)`-style single line per entry point feeding BOTH the pool options and the per-spawn `createAgentConfig`/`clientConfig`), and `processReminder`/`processSpontaneousPost` route their already-resolved `yoloDecision.enabled` into the same field. `runSharedPoolSession` gains `permissionMode` in its params (alongside today's `yoloEnabled`, or replacing it as the single threaded value) and the inline `processMessageInternal` pooled block passes the decision into `processPool.run` options. `acquireProcess` receives mode ONLY via options. The conversation-summary step stays exactly as-is (same connection, same lease) with a regression test asserting no second acquisition. Rationale: design §10 step 1 is about ordering/explicitness/coverage; changing scheduler-session decision rules would alter existing behavior the design never asked to change.

### 4. Lease serialization: zero changes to the queue, one test suite

`serviceQueue`/`executeInFlight` hold a single `inFlight` slot regardless of entry keys, so mode-split entries cannot run in parallel by construction. The preservation claim is contract-tested (design §14 "Mode/pool ownership"): a restricted session in flight, a YOLO session queued → strict serialization; both lanes and the starvation guard see the mode-split entry set as one queue. No per-mode lease, lane, or slot is introduced.

### 5. Ownership bookkeeping: two optional fields on `ActiveSession` + one audit event

`ActiveSession` gains `permissionMode?: "restricted" | "native-yolo" | "yolo-switch"` (OpenCode pooled sessions record `yolo-switch`, documenting that OpenCode mode is a per-session ACP fact, not process identity) and `processNamespace?: string` (absolute state-namespace path per Decision 2). Written once at acquisition: in the pooled runner immediately after `processPool.run` hands back the leased connector (the orchestrator's `runSharedPoolSession` and the inline message block, via a `sessionRegistry.recordOwnership(...)`-style setter reusing the existing registry), and at per-spawn spawn time in each entry point. One additive audit event `process_acquired` (`sessionId`, `agentType`, `permissionMode`, `processNamespace`, pool-key/per-spawn flag) sits beside the existing `agent_connect` event — bounded, no secrets. Row 11 consumes both fields verbatim; the delta spec's "Recovery interface is read-only consumption" scenario is the handoff gate. Alternative rejected: storing ownership on `PoolEntry` only (process outlives/reclaims independently of sessions; recovery is per ACP session — the durable per-session record must be per-session).

### 6. Directory creation and gate-context scope unchanged

`ensureSharedDirs` moves from pool-key to entry-key input (OpenCode values byte-identical; OMP entries get their mode-segmented roots — the factory already exported those paths, they simply were never created for OMP because OMP never pooled before). Gate contexts remain per ACP session on the connector (row 6/row 11 territory); nothing in the pool touches them.

### 7. Tests are consumer-visible decisions, not source snapshots

Pool unit tests (stub `connectorFactory`, existing test harness in `tests/core/agent-process-pool.test.ts`): same-mode reuse (one spawn), cross-mode separation (two spawns, distinct env namespaces), dual-mode coexistence + per-mode reclaim independence, options-carry-mode (factory receives exactly the options' mode), OpenCode byte-identity (map keys + spawned env + cwd snapshots vs current golden values). Orchestrator tests (stub pool per `createStubProcessPool` pattern): for EACH enumerated entry point, an ordering recorder proves resolution precedes acquisition/spawn and the threaded mode equals the resolved decision (global flag on, channel `yolo: true` override, and default-off cases where per-session resolution applies); summary path asserts no extra acquisition. Ownership tests assert the registry fields and audit event content at acquisition. All mock-only; nothing certifies native OMP isolation.

## Risks / Trade-offs

- **Two processes per channel doubles OMP memory pressure in mixed channels** → bounded by existing reclaim idle + lease serialization (only one ever runs at a time); accepted per design §5's explicit dual-process statement.
- **Mode segment duplicating row 9's state segment** → deliberate; docs state the split (state namespace from the factory, pool identity from options) so neither side is "simplified" away later.
- **Entry-key strings appear in logs/audit** → they embed mode; that is intended observability (`discord/123:native-yolo`) and no secret material.
- **Reordering scheduler paths risks behavior drift** → decision rule unchanged (`this.yolo`); the reorder is a hoist plus explicit threading, protected per-entry-point ordering tests.
- **Shared-file churn** (`session-orchestrator.ts` with rows 4/11/16) → edits confined to the enumerated call sites (resolution statement + one threaded field + ownership write), no refactors of surrounding flow.

## Migration Plan

Pre-release, no compatibility layer: `PoolRunOptions` gains required fields (all call sites updated in the same change); old pooled state roots are ephemeral under the bot data root and reclaim on upgrade naturally. OpenCode paths are byte-identical, so rollback is reverting one commit. No config/env/Helm synchronization is needed (mode from existing global flag + reply-policy config; agent type from row 7).
