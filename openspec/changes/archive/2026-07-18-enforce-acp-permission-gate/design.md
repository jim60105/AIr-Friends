## Context

AIr-Friends bridges untrusted Discord/Misskey chat to an OpenCode ACP agent subprocess with **no human approval step** — the ACP permission gate in `src/acp/client.ts` is the entire trust boundary. There are three permission layers documented in `docs/AGENT_PERMISSIONS.md`:

- **Layer 2** — OpenCode's own permission map in `agent-config/opencode.json`.
- **Layer 3** — this repo's `requestPermission()` in `src/acp/client.ts`.

Run-2's finding F12 established (against OpenCode source `permission/index.ts:67-107`, `Permission.ask`) that Layer 2 **short-circuits**: for an `"allow"` verdict the loop hits `continue`, `needsAsk` stays false, and the function returns *before publishing the `permission.asked` event*. The ACP bridge (`acp/event.ts:70`) forwards to `requestPermission` **only** on that event. So an `"allow"` entry never reaches Layer 3 — Layer 3 is dead code for it. `docs/AGENT_PERMISSIONS.md:147` already says as much ("the `"ask"` value causes OpenCode to forward the decision to the ACP `requestPermission()` callback rather than evaluating it internally at Layer 2"), contradicting the same doc's line-55 claim that requests "must pass all applicable layers."

Current state verified in code (HEAD `840db01`):

- `agent-config/opencode.json:46-91`: bash `"*": "deny"`, but the restricted profile allow-lists **~28 bash commands**, not a handful. Beyond the skill-invocation patterns (`deno run *skills/*`), the `"allow"` set includes `agent-browser`, `rg`, `cat`, `head`, `tail`, `ls`, `find`, `wc`, `file`, `tree`, `jq`, `bc`, `pdftotext`, `pdfinfo`, `pdfimages`, `pdftoppm`, `pandoc`, `exiftool`, `ffmpeg`, `ffprobe`, `magick`, `convert`, `identify`, `mogrify`, `unzip`, `zip`, `7zz`, `zola`. **Many of these are arbitrary-file-read primitives just like `head`** — e.g. `rg -a "" /proc/1/environ`, `jq -Rs . /proc/1/environ`, `pandoc /proc/1/environ -t plain`, `exiftool /proc/1/environ`, ImageMagick's `label:@/path` / `-verbose` file-read coders, `pdftotext /any/file -`, and archive round-trips (`zip`/`unzip`/`7zz`). Any of them reads secrets or cross-user memory today. Line 45 `"edit": "ask"` is the *only* `"ask"` in the restricted profile; every one of the ~28 bash entries self-authorizes at Layer 2 and never reaches Layer 3.
- `src/acp/client.ts`: `referencesOutOfWorkspacePath` (`~:230`) is scheme-blind — it checks for leading `/`, `~`, `$HOME`, `../` but not `scheme://`. Its own doc comment cites `agent-browser /home/deno/.git-credentials` as the threat it stops. The execute branch (`~:481-526`) approves only registered-skill command prefixes and default-rejects everything else.
- `Containerfile`: single `ARG UID=1000`, `USER $UID`, root group GID 0 (OpenShift arbitrary-UID model). `dumb-init` is PID 1. The daemon and the agent subprocess run as the **same** UID, so `/proc/1/environ` (which inherits the container env, including the daemon's secrets) and every `/app/data/workspaces/**/memory.private.jsonl` are readable by the agent.
- `src/acp/agent-connector.ts:97`: the agent is spawned via `Deno.Command(DUMB_INIT_PATH, { clearEnv: true, ... })` — no `uid`, no filesystem confinement.

Note `head`/`tail`/`ls`/`find`/`cat` are **not** registered skill `commandPrefixes`. That has a sharp consequence for the fix (see D2): the execute branch has no code path that would authorize them today — the only thing permitting them is Layer 2's `"allow"`.

## Goals / Non-Goals

**Goals:**

- Make Layer 3 (`requestPermission`) the *authoritative* decision point for file-reading bash tools, so the boundary code the project already wrote actually runs.
- Do so **without** breaking the agent's legitimate in-workspace file reads.
- Close the `agent-browser file://` path-read variant that is scheme-blind today.
- Add a filesystem confinement so that a future Layer-2 misconfiguration (or a new allow-listed tool) cannot re-expose `/proc/1/environ` or cross-user workspaces — i.e. remove the single-point-of-failure property.

**Non-Goals:**

- Changing the **YOLO** profile (`opencode.json:105` `"*": "allow"`). YOLO is an explicit operator opt-out; F12 is about the default restricted profile.
- Rewriting the agent into a fully sandboxed executor or replacing OpenCode. We harden the existing gate + add confinement.
- Backward compatibility / config migration — pre-release, zero users (per project direction).
- The network-egress leg (`webfetch`/`websearch`/`agent-browser` reaching internal URLs) — that is finding F14's separate change. This change only touches `agent-browser`'s **file://** read behavior, not its network policy.

## Decisions

### D1 — Route **every** self-authorizing bash tool through Layer 3 (`"allow"` → `"ask"`)

Change **all** the restricted-profile bash entries that can touch the filesystem from `"allow"` to `"ask"` — not a curated subset. Concretely this is the full utility set at `opencode.json:46-91`: `agent-browser`, `rg`, `cat`, `head`, `tail`, `ls`, `find`, `wc`, `file`, `tree`, `jq`, `bc`, `pdftotext`, `pdfinfo`, `pdfimages`, `pdftoppm`, `pandoc`, `exiftool`, `ffmpeg`, `ffprobe`, `magick`, `convert`, `identify`, `mogrify`, `unzip`, `zip`, `7zz`, `zola`. The skill-invocation patterns (`deno run *skills/*/scripts/*.ts*`) may remain `"allow"` because Layer 3 already has explicit entrypoint-anchored matching for them.

- **Why the *whole* set, not just `head`/`cat`:** the finding is "a Layer-2 `"allow"` bypasses the gate." `rg`, `jq`, `pandoc`, `exiftool`, ImageMagick, `pdftotext`, and archive tools are all arbitrary-file-read (or read-then-emit) primitives with the *identical* bypass. Flipping only the obvious five would ship a CRITICAL fix that leaves `rg -a "" /proc/1/environ` fully working. Every filesystem-touching entry must go to `"ask"`.
- **Why `"ask"` is the only lever:** it is the sole verdict that reaches `requestPermission`. There is no other way to make Layer 3 evaluate these commands.
- **Alternative considered — keep `"allow"` but add a wrapper binary** that re-validates paths: rejected; it re-implements the gate in a second place and still trusts the agent to call the wrapper rather than the raw binary.

### D2 — Generic-command allow-list in the execute branch, gated so **every** path argument resolves in-workspace

Extend `requestPermission`'s execute branch with a **generic-command allow-list** covering exactly the utility set moved to `"ask"` in D1. When the command's first token is on this list, approve **iff every path-like argument — input *and* output — resolves inside the session workspace or TMPDIR** (reusing `referencesOutOfWorkspacePath` plus the boundary-safe `isWithinDir` helper from run-1's F4 fix); otherwise reject with logging.

- **Why this is mandatory, not optional:** these utilities are not registered skill prefixes, so once D1 sends them to Layer 3 the *current* execute branch default-rejects them — every legitimate in-workspace use (the agent reading/searching/converting its own files) would break. D2 is what keeps the agent functional after D1.
- **Input *and* output paths, because the set is not purely read-only:** several of these tools write (`ffmpeg`/`convert`/`mogrify`/`pdftoppm` produce output files, `zip`/`unzip`/`7zz` create/extract archives). The gate must confine **all** their path arguments — so an out-of-workspace *output* target (e.g. `convert in.png /home/deno/.ssh/authorized_keys`) is also rejected, not just out-of-workspace reads. This is why the allow-list is keyed on "all path args in-workspace" rather than "read-only command."
- **Truly dangerous commands stay denied:** general shells/interpreters and mutating system tools (`python`/`git`/`gcc`/`make`/`mkdir`/`rm`/`mv`/`dd`/`chmod`/`strace`/`echo`, already `"deny"` in the config) are **not** on the allow-list and remain default-deny at Layer 3 as well.
- **Membership must be verified, not assumed:** a couple of entries need a real usage check before inclusion — `bc` (calculator; `bc file` evaluates numeric input, low file-read value) and `zola` (static-site generator that reads a project tree). If the agent does not actually need them, drop them to `"deny"` rather than allow-listing; if it does, they are gated on in-workspace paths like the rest. (Open Question.)
- **Argument parsing caveat:** whitespace tokenization is not a shell parser. `containsShellOperators()` already rejects `;`, `|`, `&`, backtick, redirects, subshells, so argument smuggling via shell metacharacters is blocked before this branch; the allow-list operates on the residual simple-argument case. This is a defense-in-depth tightening backed by D4 confinement, not a formal shell-safety proof.

### D3 — `referencesOutOfWorkspacePath` rejects any URI scheme

Add, near the top of `referencesOutOfWorkspacePath`, a check that treats any token matching `^[a-zA-Z][a-zA-Z0-9+.-]*://` as out-of-workspace (after the existing quote/`--flag=` stripping). This catches `file://`, and also defensively `http://`/`https://` when passed as a *path* argument to a file-reading command.

- **Why:** the function's own doc comment names `agent-browser /home/deno/.git-credentials` as the threat, yet `file:///etc/passwd` — the same read via a URI — bypasses it. The scheme check closes the D2 gate's blind spot for `agent-browser open file://…`.
- **Interaction with D1/D2:** `agent-browser` becomes `"ask"` (D1) and is gated at Layer 3; because `agent-browser` is a browser/fetch tool rather than a plain read command, it is **not** added to D2's read-command allow-list — its `file://` argument is rejected by D3, and its network behavior is F14's concern.

### D4 — Filesystem confinement of the agent subprocess (defense-in-depth)

D1–D3 make the gate authoritative, but leave the same single-point-of-failure shape: one wrong `"allow"` re-opens `/proc/1/environ`. Add a confinement so the agent process **cannot** read the daemon's environ or other users' workspaces even with a permissive gate.

The obvious textbook fix — run the agent under a *different UID* via `Deno.Command({ uid })` — **is not available here**: the container runs unprivileged as a single UID (OpenShift arbitrary-UID / GID-0 model), so the daemon has no `CAP_SETUID` to switch the child to another UID, and the runtime UID is not even known at build time. Options actually available:

1. **Mount-namespace confinement via a rootless sandbox wrapper** (e.g. `bubblewrap`): spawn the agent under `bwrap` (in place of, or wrapping, `dumb-init`) with a fresh mount namespace that bind-mounts only the agent's own workspace + required runtime dirs read-write, mounts a fresh `/proc` (hiding host PID 1's environ), and leaves everything else unmounted/inaccessible. **Caveat — this leans on the *same* capability the naive-UID-separation option lacks:** `bwrap` creating a new mount+user namespace needs either a setuid-root helper (defeated by `no-new-privileges`, which the restricted OpenShift `restricted-v2` SCC sets) or **unprivileged user-namespace creation**, which is commonly disabled on hardened/RHCOS kernels. So this is *not* a free win over option 3; whether it works must be verified against the actual target SCC/kernel, and if it cannot, the change must fail closed (see below), not silently run unconfined.
2. **Landlock LSM** (kernel ≥ 5.13) applied to the agent process to restrict the readable filesystem subtree to the workspace. No new binary and no namespace-creation privilege needed (a process may always restrict *itself* via Landlock), but requires a small native shim (Deno has no Landlock API) and degrades to no-op on older kernels — so it too needs a kernel-capability probe and a fail-closed path. Its lower privilege requirement may actually make it the more deployable option under a locked-down SCC; to be weighed in the Open Question.
3. **Two-account container**: build with a dedicated `agent` user distinct from the daemon user, start PID 1 as root, and have the daemon drop the agent subprocess to the `agent` UID. This gives true UID separation but **sacrifices OpenShift arbitrary-UID compatibility** (needs a known second UID and an initial-root entrypoint).

**Recommendation:** ship D1–D3 (the authoritative-gate fix) as the blocking, independently-valuable change. For confinement, **do not commit to a mechanism until it is empirically verified against the real deployment SCC/kernel** — bubblewrap and the naive-UID and `unshare`-based options all depend on namespace/capability privileges a `restricted-v2` non-root container may not grant (the same constraint the F14 network-isolation change hits, and they should be verified together). Whichever mechanism is chosen SHALL be guarded by a capability probe that **fails closed** with a clear startup error if the confinement cannot actually be established, rather than starting the agent unconfined. Landlock (option 2, self-restriction, no namespace-creation privilege) and the two-account container (option 3) are the fallbacks when unprivileged user namespaces are unavailable. The mechanism choice is the main Open Question below.

## Risks / Trade-offs

- **[D1 without D2 bricks the agent]** → the two must land together; the spec and tests assert both in-workspace approval *and* out-of-workspace rejection for the same command. CI must include a positive path (agent reads its own workspace) so a regression to "deny all" is caught.
- **[D2 allow-list is broader than skill prefixes and could admit an unforeseen read]** → restrict strictly to read-only commands, keep the list short and reviewed, and rely on D4 confinement as the backstop for anything the list misjudges.
- **[D2 whitespace tokenization ≠ shell parsing]** → `containsShellOperators()` already blocks the metacharacters that enable smuggling; document the residual and keep the list minimal.
- **[D4 bubblewrap needs unprivileged user namespaces, which some hardened hosts disable]** → fail closed at startup with an actionable message; document option 3 (two-account container) as the fallback and the OpenShift-compat trade-off it carries.
- **[D4 confinement hides a path the agent legitimately needs]** → enumerate required mounts (workspace, TMPDIR, `deno`/`opencode` binaries and caches, `agent-browser`/Chromium, `rg`, CA certs) from `agent-factory.ts`; cover agent startup + a skill run in an integration test before landing.
- **[Chromium under bubblewrap]** → `agent-browser` already runs Chromium with `--no-sandbox`; nesting it inside a bwrap mount namespace needs verification that `--no-sandbox` Chromium still launches. **If Chromium cannot run confined and `agent-browser` is exempted from the confinement, then D4's "daemon environ / cross-user workspace not readable" guarantee does NOT hold for the `agent-browser` process** — its file-read safety would rest entirely on D1–D3's argument checks (which is exactly the single-point-of-failure D4 was meant to remove, for the very tool the finding's doc-comment PoC names, `agent-browser /home/deno/.git-credentials`). If the exemption is taken, the spec's confinement scenarios SHALL be stated as not covering `agent-browser`, and that gap SHALL be called out rather than left implied by the blanket requirement text. Flagged in Open Questions.
- **[F12/F14 both touch `agent-browser` and `opencode.json`]** → the split is intentional and non-conflicting: F12 owns `agent-browser`'s **file-argument / `file://` gating at Layer 3** (D1/D3), F14 owns its **network-path mediation**. Neither edits the same config semantics in a contradictory way (both move `"agent-browser *"` off `"allow"`; F12 for the read gate, F14 for egress — the end state is `"ask"` plus mediated egress). Implementers landing them in sequence should treat the `opencode.json` `agent-browser` entry as jointly owned and reconcile to `"ask"`.

## Migration Plan

No data migration (pre-release, zero users).

1. Land D1+D2+D3 together (config + `client.ts` + tests). This is the blocking security fix and is independently shippable.
2. Correct `docs/AGENT_PERMISSIONS.md` so the Layer-2/Layer-3 relationship is described accurately (an `"allow"` verdict does **not** reach Layer 3) and document the generic read-command allow-list.
3. Land D4 confinement behind a startup capability probe; verify agent boot + a skill run + `agent-browser` in the target runtime.
4. Rollback: revert the change; no persistent state is altered. If D4 proves incompatible with the deployment runtime, D1–D3 still stand on their own.

## Open Questions

- **Confinement mechanism:** bubblewrap (D4 option 1) vs. a Landlock shim (option 2) vs. two-account container (option 3)? This is **not** decidable on paper — it depends on whether the target SCC/kernel grants unprivileged user-namespace creation. Verify empirically against the real deployment (the same probe F14's network isolation needs). If unprivileged user namespaces are available, bubblewrap is the most complete; if not, Landlock (self-restriction, no namespace-creation privilege) or the two-account container are the fallbacks. Whatever is chosen must fail closed when it cannot establish confinement.
- **Generic-command allow-list membership:** confirm each entry the agent actually needs. `rg`/`cat`/`head`/`tail`/`ls`/`find`/`wc`/`file`/`tree`/`jq`/`pandoc`/`exiftool`/`pdftotext`/`pdfinfo`/`pdfimages`/`pdftoppm`/`ffprobe` and the media/archive writers (`ffmpeg`/`magick`/`convert`/`identify`/`mogrify`/`unzip`/`zip`/`7zz`) map to real skill/agent usage; `bc` and `zola` are the doubtful ones — drop to `"deny"` if unused rather than allow-listing.
- **`agent-browser`/Chromium `--no-sandbox` inside a bwrap namespace:** does it still launch? If not, either mount the paths Chromium needs or exempt `agent-browser` from the mount-namespace while keeping D1/D3 (so `file://` is still gated).
- **Generic read-command list membership:** confirm the exact set the agent legitimately needs (`rg` and `cat`/`head`/`tail`/`ls`/`find` are certain; `wc`/`file`/`tree`/`jq` to be confirmed against actual skill/agent usage) so the list is neither too narrow (breaks operation) nor too broad.

## Resolved During Implementation (2026-07-18)

- **Confinement mechanism = bubblewrap (userns-first), but it is OPT-IN because a fresh `/proc` mount fails under doubly-nested user namespaces.** bubblewrap is the chosen mechanism (D4 option 1); `bubblewrap` is added to the `Containerfile`; confinement keeps the network **shared** (no `--unshare-net`) so the agent's loopback Skill API keeps working (network isolation is F14's concern). **However**, empirical testing under rootless podman as UID 1000 (incl. `--cap-drop=ALL --security-opt no-new-privileges`) shows that while userns/mount-namespace *creation* succeeds, **`bwrap --proc /proc` (and `--dev`) FAIL with "Can't mount proc … Permission denied"** — because rootless podman is itself a user namespace and mounting a fresh procfs inside a *second* nested userns is blocked by the kernel (adding `SYS_ADMIN` does not help; the constraint is nesting, not capabilities). A real OpenShift node that does not put the pod in a user namespace should not hit this double-nesting, but that is unverified here and the design flagged it as "not decidable on paper." Consequently: (a) `filesystemConfinement` defaults **off** and is guarded by the functional probe `probeFilesystemConfinement()` which fails closed when enabled-but-unavailable; (b) the primary F12 protection is the authoritative gate (D1–D3), which is default-on and needs no namespace privilege; (c) enabling D4 requires verifying `scripts/probe-sandbox-caps.sh` shows bwrap confinement OK on the real runtime. Landlock (option 2) and the two-account container (option 3) remain fallbacks for runtimes where the fresh-`/proc` mount is unavailable.
- **`bc`/`zola` membership:** decided **`"deny"`** (a calculator and a static-site generator; the agent needs neither) rather than allow-listing.
- **`agent-browser` under bwrap + Chromium `--no-sandbox`:** still an Open Question requiring a live launch in the dev env (tasks 4.4/4.5); if Chromium cannot run confined and `agent-browser` is exempted, the `agent-sandbox-hardening` confinement scenarios must be narrowed to exclude the `agent-browser` process (its file-read safety then rests on D1–D3 only). The `compose.yml` restricted baseline + `scripts/probe-sandbox-caps.sh` are provided to run this verification.

## Rubber-duck follow-up (2026-07-18): D2 allow-list narrowed to safe readers only

A rubber-duck review found that several tools originally in the D2 allow-list can read/write arbitrary files through their **own argument DSL** — which the lexical `resolve()`-based path check cannot see — reproducing the exact `/proc/1/environ` read F12 closes, and critically so **because D4 confinement is off by default**. Concrete bypasses: `magick -size 400x100 caption:@/proc/1/environ out.png` (ImageMagick `@`-coder, CVE-2016-3714 class), `exiftool -@ tmp/args.txt` (argfile indirection — combined with the unrestricted TMPDIR write path the agent can author the argfile), `ffmpeg -f lavfi -i movie=/etc/passwd`, `pandoc --lua-filter` (code exec), `7zz x a.7z -o/etc/cron.d/` (attached-`-o` misparsed as a relative token), and archive path traversal. Resolution: the allow-list is narrowed to **plain path-arg readers only** (`rg`, `cat`, `head`, `tail`, `ls`, `find`, `wc`, `file`, `tree`, `jq`, `pdftotext`, `pdfinfo`, `pdfimages`, `pdftoppm`); ImageMagick/ffmpeg/exiftool/pandoc/archive tools are **removed** (denied at the gate until D4 confinement — which contains them regardless of argv — is enabled+verified). Additionally a `DANGEROUS_GENERIC_FLAGS` denylist rejects the whole command for code-exec/arbitrary-target flags (`find -exec`/`-delete`/`-fprintf`, `rg --pre`, `-@`, `--lua-filter`, ...), and an attached-value out-of-workspace path (`-o/etc/...`) is rejected. The proxy-side and env-posture findings are recorded in the F14 design.
