## 4. Agent filesystem confinement (D4)

- [x] 4.1 **Empirically verify** against a `restricted-v2`-like posture whether the confinement is obtainable, BEFORE committing to a mechanism. **Verified via rootless podman (UID 1000, incl. `--cap-drop=ALL --security-opt no-new-privileges`):** userns + mount-namespace *creation* succeeds (userns-first), BUT `bwrap --proc /proc`/`--dev` **FAIL** ("Can't mount proc … Permission denied") because rootless podman is itself a userns and mounting a fresh procfs inside a *second* nested userns is blocked (SYS_ADMIN does not help). A real OpenShift node without pod-userns should not double-nest, but that is unverified. **Decision:** bubblewrap is the mechanism, but `filesystemConfinement` defaults **off** (opt-in), guarded by a functional probe that fails closed when enabled-but-unavailable; D1–D3 (default-on, no namespace needed) are the primary protection. Recorded in `design.md`.
- [x] 4.2 Wrap the agent spawn so the subprocess runs with a filesystem view that excludes `/proc/1/environ` (fresh `/proc`) and other users' workspace directories, exposing only the agent's own workspace, TMPDIR, and required runtime paths — `src/acp/filesystem-confinement.ts` (`buildBwrapConfinement`) wired into `src/acp/sandbox-manager.ts`; `bubblewrap` added to the `Containerfile`
- [x] 4.3 Add a startup **functional** capability probe (actually attempt the confinement operation, e.g. `bwrap … true` — not a mere `which` check) that fails closed with an actionable error if confinement cannot be established — `src/acp/sandbox-capabilities.ts` (`probeFilesystemConfinement`/`canConfineFilesystem`); `SandboxManager.buildSpawnOptions` throws when confinement is required but unavailable
- [x] 4.4 Verify `agent-browser` (Chromium `--no-sandbox`) still launches under the confinement. **VERIFIED in the built image: `chrome-headless-shell --no-sandbox --headless` launches successfully inside the exact `buildBwrapConfinement` mount namespace (run under `podman --privileged`, the local env where bwrap can mount a fresh `/proc`). No exemption needed — the confinement scenarios cover `agent-browser`.**
- [x] 4.5 Assert the confined agent cannot read `/proc/1/environ` or a sibling user's workspace, and CAN read its own workspace. **VERIFIED in the built image (real `buildBwrapConfinement` args): with the filtered spawn env (as SandboxManager + clearEnv provide), the sandbox `/proc/1/environ` carries NO daemon secret and the daemon PID is absent from the sandbox pid namespace; a sibling user's `memory.private.jsonl` and its directory are hidden; the session's own workspace is readable. Argv + fail-closed logic also unit-tested (`tests/acp/filesystem-confinement.test.ts`, `tests/acp/sandbox-manager.test.ts`).**
