## Why

Design §7 requires that no untrusted executable top-level code can run inside an OMP process: `--no-extensions` plus the exact `--trusted-extension` argument is necessary, but P0 recorded it is **not** a complete boundary — at the pin, SDK custom-tool discovery/import runs independently of extension flags and imports a module before any factory/name inspection. Row 12 turns that verdict into the AIr-owned trusted-extension module's pre-import bootstrap contract, exact owned-module ownership, and canonical critical-skill selection, with fail-closed session setup and honest application gates where the pinned binary offers no supported mechanism.

## What Changes

- Author the deployment-owned trusted-extension module tree (development tree at the path `OMP_TRUSTED_EXTENSION_PATH` exports from `src/utils/omp-paths.ts`; the final installed location is row 20's, honoring this contracted path). The module's load-time bootstrap computes and freezes one exclusion decision over every P0-audited discovery/import surface **before** any untrusted executable tool/plugin module could import: native custom-tool discovery roots, plugin entry points, configured module roots, workspace-owned dependencies, and symlinked/linked roots. The per-surface mechanism table (each labeled supported / candidate-to-verify / no-supported-mechanism per the pinned source): ambient extension discovery — `--no-extensions` plus the exact canonical trusted module in the `main.ts` `buildSessionOptions` trusted-path branch, **supported for that surface only**; SDK custom-tool discovery (`sdk.ts` `discoverCustomToolPaths`/`loadCustomTools`, `custom-tools/loader.ts` `loadTool` importing before factory/name inspection) — **no-supported-mechanism**, P0's unresolved blocker; plugin entry points (`plugins/loader.ts` `getEnabledPlugins` including project roots and linked dependencies) — **no-supported-mechanism**, P0's unresolved blocker; configured module roots (`PI_CONFIG_FILES`/`OMP_PROFILE`/`PI_PROFILE` selectors) — **candidate-to-verify** via deployment env posture only (rows 7/8 never export, row 9 never sets; no native per-root exclusion traced); workspace-owned dependency discovery — **candidate-to-verify** via row 9's deployment-derived neutral launch cwd whose dependency/`.omp` layers are empty by construction; symlinked/linked roots — **candidate-to-verify** via canonical identity verification (row 2), which can *detect* escapes but cannot make the native loader not import them. `withHostGuard` and SDK `preloadedCustomToolPaths` are explicitly NOT import guards (P0) and the change invents no loader hook.
- Fail-closed session setup: the bootstrap's decision is consumed during trusted-module initialization; when the required exclusion cannot be established for any surface, trusted-module initialization fails and the affected `session/new`/`session/load` fails with an ACP request error naming the unestablished surface — observable to the client through the existing `AgentConnector.createSession()`/`raceAgainstCrash` error path. Setup never degrades to a partially guarded session, and a post-import tool-name filter or lifecycle allowlist is never treated as evidence.
- Exact owned-module ownership: only the row-9 contracted module path plus its pinned, image-owned dependency closure (row 20's checksummed install) is trusted; anything occupying a workspace/HOME/npx-discoverable path gains nothing, and any candidate matching a critical skill/tool NAME gains nothing (name-only trust rejected per P0). Symlinks leaving the owned root are untrusted, reusing row 2's canonical owned-root identity (canonical path, dev/ino observation, disjointness from writable roots) — never a second canonicalizer.
- Critical-skill selection: pin the AIr-owned skills directory canonically (row 2 trusted-skills root + P0 `CriticalSkillContract`); exclude untrusted project/workspace discovery from critical-name resolution so a same-name workspace/project file or escaping symlink never resolves a critical skill; ordinary skills stay globally enabled — only critical-name resolution is ownership-pinned. The ownership decision holds on new (`session_start`/initial skill snapshot), load (recovery re-discovery), and refresh (`setActiveSkills`-style registry transitions): every resolution consults the current canonical selection/resource generation; a stale generation or old-session snapshot fails. The authenticated readiness channel and deny-until-ready prompt gate are row 13's; this change wires only the ownership data row 12 produces.
- Honesty gates: record P0's two blocking verdicts as named data + application gates with explicit user-decision language, exactly as rows 8/9 shipped the record-reset gate: pre-import exclusion — extension flags alone incompatible as a complete boundary, supported full mechanism unresolved; critical-skill ownership — name-only trust incompatible, canonical selection unresolved. Own unit/mock tests validate the DECISION LOGIC (which roots/paths/names are excluded, fail-closed error shape), never that the native binary enforces it.
- Explicit non-goals (owned elsewhere): the authenticated readiness control channel and client prompt gate (`gate-omp-policy-readiness`, row 13); restricted tool inventory/provenance execution policy and alternate-entry (URI/device) blocking (`enforce-omp-restricted-tool-policy`, row 14); LSP disablement (`disable-restricted-agent-lsp`, row 15); binary/notice/module checksum and installation packaging (`package-pinned-omp-runtime`, row 20); transport (`control-omp-url-fetch-transport`/`adapt-omp-web-search`/`adapt-omp-public-code-search`, rows 17–19). Factory launch arguments (row 9), overlay content/schema keys (row 8), pool identity (row 10), and session recovery ownership (row 11) are consume-only.
- No new `config.yaml`, `.env`, or Helm field: the owned module path, owned skills root, and dependency-closure roots are source constants (or derived through `omp-paths.ts`/row 2 identities) layered on row 8's existing overlay posture. `config.example.yaml`, `.env.example`, and `helm/values.yaml` are intentionally unchanged; if implementation surfaces any new field, this change must synchronize all three files itself rather than defer.

None. Reuse the existing ACP integration capability; discovery-guard requirements extend it rather than fork a parallel security specification.

### Modified Capabilities

- `acp-integration`: Add requirements for the trusted-module pre-import discovery-exclusion bootstrap with per-surface mechanism status and fail-closed ACP session-creation errors; exact owned-module trust scope including name-only non-trust and symlinked owned-root escapes; canonical critical-skill ownership pinned across new/load/refresh while ordinary skills remain globally enabled; and the two P0 blocking application gates restated as named data with explicit user-decision requirements. P0 compatibility requirements, row 2 root identities, row 8 overlay requirements, and row 9 spawn requirements are consumed unchanged.

No factory/connector/client/pool edits, no P0/row-2/row-8/row-9 artifact edits.

Application is gated by two restated P0 verdicts (see Batch and design): full security consumption of OMP session setup stays blocked until the pre-import exclusion mechanism and critical-skill canonical selection each have a source-backed supported mechanism adopted via an explicit user decision. Mocks here prove decision logic only; the pinned official binary is absent from development environments, and no test in this change claims native enforcement.
