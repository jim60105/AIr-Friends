## Why

Design §6's code-search row and D4 require the restricted OMP deployment to preserve public code/documentation search alongside local search, and 14a keeps the `public code/docs search` inventory entry at `allow-gated-pending-adapter` for this row to complete — yet the source audit at both pins says the assumed parity target does not exist: OpenCode `1.18.21` **removed** its `codesearch` tool upstream (commit `2481dde36d9aeb48de9fb21ffd2cfdc1d42804f1`, "chore: remove codesearch tool (#27019)", 2026-05-12; the tag tree has no `packages/opencode/src/tool/codesearch.ts`, and the `codesearch: "allow"` rule in `agent-config/opencode.json` therefore binds to no shipped tool id), and **no grep_app/gh_grep skill or `GREP_APP_API_TOKEN`/code-search-token plumbing exists anywhere in this repository** (repo-wide search: the only `GITHUB_TOKEN` consumers are git-backup/git-credential and an MCP config example; the `opencode` agent env set carries no GitHub credential at all). Pinned OMP `v18.6.1` has no code-search tool in `BUILTIN_TOOL_NAMES` and no gh_grep-style search provider; its only public-code-search surface is the `github` tool's `search_code` operation, which shells out to the external `gh` CLI (`tools/gh-search.ts` `executeSearchCode` → `utils/github.ts` `gh api` subprocess with `...process.env`) — a binary absent from the image, with an auth store outside row 7's credential set and a subprocess transport the row-17 decision core cannot observe. The honest completion for this row is therefore: keep public code/docs content reachable through the routes rows 17/18 already completed, define a credential-gated adapter contract for a dedicated public-code-search tool that selects only a supported backend if one exists, and record the capability gap as a fail-closed `userDecisionRequired` route rather than fabricating a backend, promoting a never-pass secret, or admitting keyless scraping.

## What Changes

- **Freeze the parity audit as machine-readable route data with citations.** What OpenCode provides *today at the pin*: no public-code-search tool (removed upstream before 1.18.21; the opencode.json permission key is inert because permission rules bind to registered tool ids); public code/docs *content* remains reachable only through `webfetch`-style URL reads (row 17's domain) and the Exa/Parallel hosted-MCP web search (row 18's domain, `packages/opencode/src/tool/mcp-websearch.ts`). The batch's premise of grep_app/gh_grep external skills with operator-configured `GITHUB_TOKEN`/`GREP_APP_API_TOKEN` skill env vars is **false at the pins**: the shipped `skills/` tree contains no code-search skill, `GREP_APP_API_TOKEN` appears nowhere in the repository, `externalSkills` (`src/core/skill-installer.ts`, `npx --yes --package=skills skills add`) is a generic operator mechanism that ships no such skill, and neither token is in row 7's `omp` credential set or the current `opencode` set. The pinned OMP audit finds **no gh_grep-style provider** (cite `tools/builtin-names.ts`, `tools/index.ts` registries, `web/search/provider.ts` loader registries — code/searchcode/sourcegraph surfaces are fetch-pipeline scraper handlers, not search backends).
- **Define the public-code-search adapter contract as a pure decision + interface module `src/acp/omp/code-search-transport.ts` plus route table `src/acp/omp/code-search-routes.ts`**, mirroring row 18's delegation pattern: every network hop (search endpoint request and any result-enrichment subrequest) delegates to row 17's `decideFetchHop`/`planFetchRoute` in `src/acp/omp/fetch-transport.ts` — the same single `ssrf.ts` classifier, the same enforcing (`egressProxy && !unrestrictedEgress`) validating-proxy vs operator-`unrestricted` posture with pass-through preserved, `MAX_REDIRECT_HOPS = 5` manual per-hop revalidation, credential-free `{ host, hopIndex, decision, reason }` records. `fetch-transport.ts`/`fetch-routes.ts` are consumed per their contracts, imported, **never edited**.
- **Tier every candidate route `supported / candidate-to-verify / no-supported-mechanism` with citations, honestly:**
  - **no-supported-mechanism under the current credential set** — the GitHub Code Search API route (`api.github.com/search/code`, the same API OpenCode's removed tool and OMP's `gh-search.ts` `executeSearchCode` wrap): a dedicated adapter *would* use the exact credential mechanism the deployment operator may already have configured (`GITHUB_TOKEN` in the deployment env — not a new field), and consuming an already-configured operator value is *not* "requiring an unrelated vendor secret merely to select OMP" **if** that same operator configured it for a compatible purpose; **but** at today's pins `GITHUB_TOKEN` is (a) never passed to either agent env (the `opencode` `AGENT_TYPE_ENV` set carries no GitHub credential; 14a's `NEVER_PASS_ENV` puts `GITHUB_TOKEN` on the never-pass list because its registered purpose is git-backup/git-credential, and promoting it into the restricted agent process expands a repo-write-scoped secret's blast radius), and (b) its use as a code-search credential is a *new consumer role* that the batch's credential rule does not authorize this change to introduce. Route tier: `no-supported-mechanism` with `userDecisionRequired` — the decision is whether to provision a read-only code-search token through the supported config path (row 7's mechanism), never a silent GITHUB_TOKEN promotion.
  - **no-supported-mechanism** — the pinned native `github` tool's `search_code`: requires the external `gh` binary (absent from the `Containerfile`), gh's own auth store (`gh auth login`/keyring; `utils/github.ts` spawns `gh` with inherited env — and `GITHUB_TOKEN`/`GH_TOKEN` are never-pass anyway), and its subprocess HTTP bypasses the row-17 decision core (env-proxy best-effort is non-enforcement, no per-hop validation). 14a's inventory default-denies the `github` tool; this change never adds a second transport path around the adapter.
  - **candidate-to-verify, NOT selected** — keyless scraping code-search surfaces in the pinned source (the `searchcode.com` and Sourcegraph special handlers, `web/scrapers/searchcode.ts`, `web/scrapers/sourcegraph.ts`): they need no secret but are operator-unconfigured arbitrary-provider scraping backends, exactly the class row 18 refused to select; admitting a *tool* over them would add arbitrary-provider config, which this change never does. Their existence as secondary handlers **inside row 17's completed URL-read route** is separate and unchanged: a `read` of a public searchcode/sourcegraph/readthedocs URL already flows through the controlled transport (cite `tools/fetch.ts` `loadSpecialHandlers` → `web/scrapers/index.ts` `specialHandlers`).
  - **no adapter mechanism selected this row** — because every backend-specific route tiers non-supported, this change registers **no trusted-extension tool** (registerTool remains the named completion mechanism should a P0 revision + user decision provision a supported credential; then this change's route-table shape plus row 18's 6th-serial-sibling pattern complete it without re-deciding).
- **Interface parity contract (spec-locked for whenever a supported backend lands):** query parameter pass-through; result carries useful code/doc **excerpts** with **source attribution** (repository name/owner, file path, per-item source URL) and language metadata — the observable fields of both pinned formatters (`gh-search.ts` `formatSearchCodeResults` path/repo attribution; the removed OpenCode tool's grep.app-style name/path/repository/code-shape); bounded result size mirroring pinned bounds (`gh-search.ts` `SEARCH_LIMIT_DEFAULT = 10`, `SEARCH_LIMIT_MAX = 50`, text-match preview limit 50; bounded excerpt bytes per item documented); and row 18's error rules **verbatim**: authentication/rate/HTTP/malformed failures surface as honest tool errors in the native failure-message shape, **never** fabricated results, **never** an unguarded transport retry outside the controlled path, **never** an agent switch; zero-results is an honest empty outcome distinct from error.
- **Additive seam updates only:** 14a's `public code/docs search` inventory row gains a `completing-adapter` marker ONLY where this change's contract is satisfied — i.e., conditionally-gated completion data that stays `blocked_pending_adapter` under the current no-supported-credential state (the marker names the adapter contract + route table so a future credential provisioning flips the route without any 14a table-shape revisit; while no supported backend exists, the row's effective outcome is unchanged and a test pins that); row 17's `fetch-routes.ts` `search-provider.subrequests`-style public-code-search subrequest rows are consumed per their contract and the cross-table agreement test pattern from row 18 is reused to pin the two tables never disagree on a replaced route; 14b's composition distinguishes completed from pending unchanged.
- **Acceptance is deterministic unit/mock ONLY:** mocked search-endpoint/DNS/redirect fixtures assert allow/deny/routing decisions under both egress postures, credential-presence decision inputs (token present via mocked config fixture / absent), excerpt/attribution/error/empty-result shapes against the pinned observable shapes, the blocked-route fail-closed gap with `userDecisionRequired` and zero issued requests, unrestricted-egress pass-through posture, and credential-free records. NOTHING contacts the network. Native-tool reality — whatever the compiled OMP actually exposes and whether a future registerTool completion is honored — stays on the design section-15 user checklist; no mock clears the pending verdict.
- **Explicit non-goals (owned elsewhere, named):** generic web search (row 18, landed — no web-search work here), local grep/glob/find native search (native, allowed by the 14a inventory, unchanged), LSP as search (D5 forbids; stays denied), new vendor credentials/env fields (`GITHUB_TOKEN`/`GH_TOKEN` are NEVER_PASS today; this change introduces NO new field and does not re-point them; `config.example.yaml`/`.env.example`/`helm/values.yaml` sync is owed only if a NEW field genuinely surfaces, and consuming an existing operator value would be row 7's credential-set decision, not a docs-sync event), packaging (row 20), the `github` tool's non-search operations (14a owns its deny), MCP-based operator integrations (operator-controlled surface, client-owned, no feature here), native binary builds and live verification.
- **No new `config.yaml`, `.env`, or Helm field:** inputs are the existing egress posture (`agent.sandbox.egressProxy`/`egressProxyPort`/`unrestrictedEgress`/`egressAllowHosts`) consumed via row 17's core and, for any future supported route, a credential that row 7's approved config path would deliver. If implementation surfaces any new field, this change synchronizes the three config documents itself.

## Capabilities

### New Capabilities

None. Reuse the existing `acp-integration` capability; the public-code-search requirements extend it alongside row 17's URL-fetch and row 18's web-search requirements rather than fork a parallel network specification.

### Modified Capabilities

- `acp-integration`: Add requirements for the public-code-search adapter contract and honest route tiering over the pinned OpenCode/OMP surfaces (parity target removed upstream at the pin; no gh_grep-style supported backend assumed), all adapter network hops delegated to the row-17 controlled transport with the operator unrestricted-egress posture preserved, the interface-parity contract (excerpts + source attribution + repo/path metadata + documented result-size bounds + row-18 error/empty rules verbatim), the credential-gated fail-closed gap with `userDecisionRequired` and never-promoted NEVER_PASS secrets, the additive route-scoped 14a seam marker plus cross-table agreement with row 17's registry, and the mock-only acceptance boundary. P0's transport verdict, row 7's credential set, 14a/14b seam semantics, and row 18's honesty rules are consumed verbatim.

## Impact

Eventual implementation owns: the pure decision/interface module `src/acp/omp/code-search-transport.ts` and the route enumeration `src/acp/omp/code-search-routes.ts` (both new, exclusive to this change until consumers land); the additive seam-data update to 14a's public-code-search row only (conditional completion data, route-scoped); tests under `tests/acp/` (mock endpoint/DNS/redirect fixtures, interface-shape and route-table suites); the code-search section of `docs/OMP_NETWORK.md` (row 17's file — appended, not rewritten) and one `CHANGELOG.md` entry. `src/utils/ssrf.ts`, `src/utils/egress-proxy.ts`, row 17's `fetch-transport.ts`/`fetch-routes.ts`, row 18's `search-transport.ts`/`search-routes.ts`, 14a's decision tables, and 14b's composition are read-only imports. No trusted-extension sibling is registered in the current no-supported-credential state; the 6th-serial-extension slot in the 12→13→14b→17→18 tree is reserved by this change's contract (registerTool completion mechanism) for the post-provisioning follow-up and is NOT consumed now, which also de-risks row 20's digest.

Application gate inherited from P0/rows 17/18: the transport-adaptation boundary verdict is PARTIAL and the native-hook claim remains user-owned. This change's honest verdict is stronger than a mechanism gap: **no supported public-code-search backend exists under the approved credential set at these pins**, and the OpenCode parity baseline itself no longer ships a code-search tool; the route stays blocked with a documented capability gap and an explicit user decision (provision a read-only code-search credential via the supported config path, or accept the gap), never a fabricated fallback, never a NEVER_PASS secret promotion, never keyless scraping.
