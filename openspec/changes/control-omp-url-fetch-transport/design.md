## Goals / Non-Goals

**Goals:** One pure decision core that owns every URL-read transport decision under enforcing egress; a machine-readable route table that says, per pinned route, `completed-by-adapter` (supported, cited), `partial-seam-not-selected`, or `blocked-pending-adapter` with `userDecisionRequired`; additive completion of 14a's URL-read seam row; deterministic mock-only certification of decisions; honest preservation of the operator unrestricted-egress posture.

**Non-Goals:** No web-search/code-search provider work (18/19), no change to OpenCode attachment/SSRF behavior, no sandbox/egress config default changes, no packaging, no empty-netns/kernel-guarantee work, no live network calls or native binary runs, no new config/env/Helm fields, no modification of `ssrf.ts`, `egress-proxy.ts`, row 4's sinks, or 14b's composition table.

## Decisions

### D1. Pure decision core with injectable transport and DNS; native replacement stays outside the core

`src/acp/omp/fetch-transport.ts` exports `decideFetchHop(input, deps)` and `planFetchRoute(input, deps)`, pure over injected `{ resolveHost, policy }` where `policy` is the consumed egress posture (`enforcing` = `egressProxy && !unrestrictedEgress`; `unrestricted` operator posture; both derived from existing config values, never recomputed). Decisions: `allow-direct`, `allow-via-proxy`, `block { reason }` with reason codes reusing the `SsrfValidationError` classifications plus adapter codes (`hop-limit-exceeded`, `egress-policy-unresolved`). The redirect loop is adapter-owned: `redirect: "manual"` at every attempt, validate hop N+1 from the `Location` header against the same rules before issuing hop N+1, hop 1 = initial URL, cap `MAX_REDIRECT_HOPS = 5` imported from `ssrf.ts`, excess blocks. Rationale: design §9 ("per-hop redirect … validation lives IN the adapter decision logic"). Rejected: relying on `safeFetch` directly as the adapter — it hardcodes its own fetch execution and cannot express proxy-route selection or text/binary shapes for the extension-side caller; the adapter imports its validators and rule set, keeping `ssrf.ts` the single classifier (P0 fixture rule: no second SSRF classifier).

### D2. `registerTool` name replacement of `read` is the selected supported mechanism; `fetchOverride` is not

The trusted-extension tree gains a sibling module registering a `read` replacement: URL-shaped inputs (`parseReadUrlTarget`-equivalent detection of the `http(s)` branch, including selectors) are served entirely by the adapter (text route for pages/markdown, binary route for image/convertible/archives mirroring the native content-type branching), and every non-URL input delegates verbatim to the captured native via `ctx.invokeTool` (S8). This intercepts S3/S4/S5 for URL reads because the adapter replaces `loadPage`/`fetchBinary` with its own validated requests — the native global-fetch functions are never invoked on the URL path. S9 is why the alternative — injecting `ToolSession.fetch` — was rejected as the primary mechanism: the seam exists but nothing supported sets it under ACP bootstrap, so it covers only enrichment (S2) and would leave the primary/binary/secondary hops native. `fetchOverride` coverage is retained in the route table as `partial-seam-not-selected` with the exact enrichment scope cited, so a future P0 revision could promote it without revisiting this design. Rejected: wrapping `globalThis.fetch` process-globally inside the OMP process (unscoped, would capture provider/model traffic and break loopback Skill API; no supported injection point either), and patching/forking (D3).

### D3. Route table as data; completion is per-route, never blanket

`src/acp/omp/fetch-routes.ts` exports the enumeration `{ routeId, mechanism, status, citations, userDecisionRequired? }` over at minimum: `read.url-branch.text`, `read.url-branch.binary`, `read.url-branch.secondary-hops` (all `completed-by-adapter` via D2), `enrichment.reader-providers` (`completed-by-adapter` when served inside the replacement; `partial-seam-not-selected` natively), `native.loadPage.direct`, `native.fetchBinary.direct`, `search-provider.subrequests`, `code-search.subrequests` (`blocked-pending-adapter`, the first two owned by any residual native caller, the latter two owned by rows 18/19). 14a's URL-read inventory row gains the additive `completing-adapter` marker pointing at this table; rows 18/19 keep `allow-gated-pending-adapter`. The marker is consumed by 14b's existing composition distinction between completed and pending routes — composition order and error vocabulary are untouched (14b requirement: no new decision logic in wiring; a route completing is data, not logic). Rationale: the assignment's "never silently native for private-target risk" is structural: a route absent from the completed set stays blocked by 14b, so drift fails closed.

### D4. Policy-selected proxy routing; unrestricted posture untouched

In `enforcing` posture, `planFetchRoute` returns `allow-via-proxy` for validated targets and the transport executes against `getRunningEgressProxyUrl()`; the adapter performs its own SSRF validation **in addition** to the proxy's (defense in depth: a validated proxy is still consulted per hop). In `unrestricted` posture the adapter still validates per hop — that is the documented model target decision — but routes directly and performs no new denials beyond the shared SSRF rules OpenCode-equivalent fetching already applies, preserving the operator's chosen posture and D6. `egressAllowHosts` is honored through the existing proxy-side exemption (metadata-space addresses remain non-exemptable); the adapter adds no second allowlist. `HTTP_PROXY` env routing remains best-effort and is documented as non-enforcement in both `docs/OMP_NETWORK.md` and the `AGENT_PERMISSIONS.md` cross-link.

### D5. Trusted loopback/provider traffic is categorically separate

The Skill API loopback endpoint, operator-configured provider endpoints, and the proxy endpoint are deployment transport facts fixed at spawn (rows 9/12 own the env they carry); they are not inputs to `decideFetchHop`, which sees only model-supplied/derived URLs. The decision core has no code path that widens target rules because a trusted loopback call exists; tests assert a model URL targeting loopback/private/ULA/link-local/metadata spaces blocks in enforcing posture while the Skill API remains reachable through the untouched existing loopback path (design §9). `pi-internal://` and custom schemes reach the URL branch only as rejected alternate-route inputs already denied by 14a — the replacement never proxies them.

### D6. Text/binary distinction and no-credential logging

The text route mirrors the native shape (bounded body, content-type sniff for HTML/markdown); the binary route returns bytes with a `content-length` pre-check and streaming cap, plus `content-disposition`/extension hints, matching what the replacement needs to reproduce native `fetchBinary` semantics without invoking it. Decision records and adapter logs carry `{ host, hopIndex, decision, reason }` only — no URL userinfo/query, no headers, no payload bytes, no provider credentials; the log-redaction posture matches row 14b's bounded error fields. Rejected: logging final URLs verbatim for debugging (query strings carry credentials).

### D7. Test surface is decisions, not plumbing

Mocked `globalThis.fetch` (never invoked for real), mocked `resolveHostAddresses`-shaped DNS, synthetic 3xx chains: allow public hop chains (direct under unrestricted, via-proxy under enforcing); deny loopback/private/link-local/ULA/unspecified/multicast/metadata at hop 1 and at hop N (public → private redirect blocks at the hop, proving re-validation); 6-hop chain blocks with `hop-limit-exceeded`; text vs binary shape assertions; both posture selections from policy inputs; record-scan tests for credential/query absence; route-table tests assert completed/blocked verdicts and that blocked rows carry `userDecisionRequired`; a test asserts the completed-route marker never covers search routes. Per P0's fixture rule, positive native-mechanism fixtures are labeled synthetic route data — they certify the table's shape, not the binary's behavior. Real-adapter evidence remains the section-15 checklist item "Observe actual native fetch/search … traffic through the configured adapter/proxy."

## Risks / Trade-offs

- **Replacement drifts from native `read` semantics** (selectors, artifact materialization, truncation) → the replacement delegates 100% of non-URL inputs to the captured native and reproduces only the URL branch's observable output shape; regression risk is bounded to URL reads and lands on the user checklist; a same-URL decision-equivalence fixture compares adapter-route selection per native code path.
- **The `registerTool` replacement mechanism could prove unusable in the real binary** (S7/S8 are static reads) → it is the only candidate P0 left open; if the section-15 observation disproves it, the honest outcome is the P0 revision + user decision path, with 14b's `rejected_pending_adapter` standing meanwhile (fail-closed), which is exactly the design's escalation, not a silent cut.
- **Enrichment providers inside a delegated native call could reach private targets** → enrichment runs only inside the adapter-served URL branch whose initial URL already passed per-hop validation; reader-provider secondary URLs are validated as secondary hops; the remaining residual (native enrichment code paths the replacement re-implements) is enumerated in the route table rather than assumed.
- **Double-validation divergence** (adapter blocks, proxy would allow, or vice versa) → both derive from the same `ssrf.ts` rules; the adapter blocks first, so the observable decision is the stricter one; divergence tests pin that the adapter never allows what `ssrf.ts` rejects.
- **Unrestricted-posture deployments could perceive the adapter as a new denial** → tests assert the unrestricted fixtures allow everything OpenCode-equivalent fetching allows (public targets, ≤5 hops), so only private/metadata/hop-limit blocks — the shared rule set — appear, and docs state the posture difference explicitly.
- **Shared-file exposure is serial and small** → new files exclusive; trusted-extension tree is the fourth serial extension (12→13→14b→17) before row 20's digest; 14a seam edit is marker-only; `AGENT_PERMISSIONS.md`/`CHANGELOG.md` append/cross-link.

## Migration Plan

Additive: pure modules + one extension-tree sibling + marker data land behind the existing restricted launch path (restricted sessions only; YOLO registers no replacement, per 14b posture). Rollback = remove the sibling module's attach; every URL read reverts to 14b's `rejected_pending_adapter` block — never to unadapted native transport — so rollback is fail-closed by construction. No config, state, or data migrations; OpenCode flows untouched.
