## Why

Design §6 requires the restricted OMP deployment to survive an audit of the **complete** pinned tool inventory and its implicit side effects — "not only tools listed in the handoff YAML" — with default rejection for unknown tools and internal schemes, live-origin checks that name-match cannot satisfy, and no hidden mutation/debug/device route admitted merely because `read` or `write` is allowed. Row 13 ships the readiness SIGNAL and prompt gate around this boundary but carries zero policy content ("row 14 fills the slot"), and rows 1/8/5 recorded that neither the settings-layer record reset nor complete native destructive decoding works at the pin — so the restricted **execution-time default-deny decision** is the operative boundary, and it does not exist yet as code. Row 14 was split for size: this change (14a) authors the pure decision modules only; the trusted-extension `tool_call` handler wiring that consults them per call is 14b (`wire-omp-restricted-tool-enforcement`), and the generic-command path canonicalization is 14c (`harden-acp-command-path-gate`).

## What Changes

- Add a pure restricted tool-inventory decision module over the pinned complete OMP tool list plus its implicit side-effect surfaces: every decision is a pure function of tool name + recorded provenance + decoded input shape. Allow rows: read/list/glob/grep and search-class tools gated to the existing row-4 filesystem boundaries (including the native note that some native implementations do not automatically invoke ACP callbacks — the decision is applied at the handler, not assumed); `bash` gated to the existing common command policy (its path-argument lexical→canonical hardening is 14c, unchanged here); write/edit routed to the row-4/row-8 sinks, todo state session-scoped with no filesystem mutation route; MCP tools operator/client-owned and admitted through the provenance decision below. DEFAULT-DENY: every unknown tool and every OMP-only execution surface outside the approved capability set — eval, task/subagent, computer/browser, async, launch, debug, AST mutation/edit, LSP-referenced config, SSH, `xd://`-style internal device schemes, and config-write — including surfaces reached through implicit side effects of otherwise-allowed tools, not just the handoff YAML list.
- Add the live-provenance DECISION: given a tool's recorded origin (owned trusted extension / operator MCP / host / workspace), decide admit or deny; name-match alone is structurally insufficient and a same-name workspace/host or unowned-discovery tool is denied even when the name is on the allow table. An operator MCP tool **refreshed or registered after startup** is admitted by the decision (subject to freshness of the live registry observation) — this change ships the decision, not the registry-refresh plumbing.
- Add alternate-execution-entrypoint BLOCKING decisions: a denied or gated capability reached via a different tool, internal URI scheme, or device (e.g. execution through an internal scheme, config write flipping approval posture, debug/AST/LSP-adjacent mutation, SSH device routes) is rejected even when the underlying capability's ordinary tool is allowed; the decision keys on the capability and route pair, never on the underlying tool's allow status alone.
- Add exact-keys native approval-record interpretation with NO inherited grants, consuming row 8's surviving-lower-record verdict: because `Settings.#readConfigOverlays` folding means lower-layer `tools.approval` grant/prompt/deny records can persist into an OMP process, the interpreter reads only the exact registered tool keys, never OpenCode's wildcard default-deny, NEVER derives an allow from a surviving lower-layer `allow`/`prompt` record, and models the surviving-record behavior faithfully as the reason the restricted execution-time default-deny (this module) — not settings-layer clearing — is the operative boundary. No working record reset is asserted anywhere.
- Consume row 5's shared destructive module: a pure decision entry that, given a decoded complete destructive intent, returns the common all-target decision by delegating to `src/acp/destructive-policy.ts` normalization and its exported conformance table — no second normalizer, no re-derivation; an incomplete/unparseable intent yields the shared fail-closed verdict with zero side effect.
- Add the MCP admission decision with mechanism status honestly tiered: the pinned P0 ledger has **no MCP boundary row**, so the admission decision's mechanism basis is labeled `candidate-to-verify` / `needs-mechanism-audit`, never `supported`; the decision requires no generic human elicitation/form UI (explicitly absent, per design §5/§7).
- Restate the honesty gate as named data: P0's record-reset **INCOMPATIBLE** verdict and destructive-intent **UNRESOLVED** verdict are carried with `userDecisionRequired: true` (shape mirroring row 8's `recordResetGate` and row 13's gate); these modules ship as the restricted default-deny that holds the boundary pending those user decisions, and no mock clears either gate.
- Scope honesty as data and tests: the decision modules are consulted ONLY in restricted mode — native-YOLO OMP sessions receive NONE of these clamps (design D6) and OpenCode flows are untouched; the modules are pure (no IO, no handler registration, no wiring).
- Explicit non-goals (owned elsewhere): trusted-extension `tool_call` handler WIRING of these decisions incl. per-call live provenance and post-start MCP registry-refresh admission plumbing (14b `wire-omp-restricted-tool-enforcement`); generic-command gate path lexical→canonical hardening (14c `harden-acp-command-path-gate`); restricted LSP disablement implementation incl. implicit startup (row 15); transport (rows 17–19); packaging (row 20); readiness signal/gate (row 13, consumed); destructive normalization and conformance fixtures (row 5, consumed); overlay authoring and `tools.approval` composition (row 8, consumed); pre-import exclusion (row 12, consumed); P0 contract redefinition.
- No new `config.yaml`, `.env`, or Helm field: the inputs are in-code tables plus predecessor contract values. `config.example.yaml`, `.env.example`, and `helm/values.yaml` remain intentionally unchanged; if implementation surfaces any new field, this change synchronizes all three itself.

## Capabilities

### New Capabilities

None. Reuse the existing ACP integration capability; the restricted tool decision requirements extend it rather than fork a parallel security specification.

### Modified Capabilities

- `acp-integration`: Add requirements for the restricted tool-inventory default-deny decision table over the complete pinned inventory with implicit side effects, the live-provenance admission decision (including post-start operator MCP refresh admission), alternate-execution-entrypoint blocking, exact-key approval-record interpretation with no inherited grants under the surviving-lower-record reality, the destructive-intent decision consumed from the shared conformance table, the honestly-tiered MCP admission decision, the two restated P0 application gates with user-decision markers, and the restricted-only consultation posture (YOLO exempt per D6, OpenCode unaffected). P0 contracts, row 4 sink policy, row 5 shared destructive module, row 8 overlays/gate, and row 13 readiness requirements are consumed, not redefined.

The modules import — never edit — `src/acp/filesystem-policy.ts` (row 4), `src/acp/destructive-policy.ts` (row 5), `src/acp/omp/compatibility-contracts.ts` (P0), and row 8's owned-settings gate data; they register nothing, read nothing from disk, and touch no client/connector/extension file. 14b is the first consumer (handler wiring per call); 14b/14c and rows 15/17–22 are unchanged.

Application gate inherited from P0 via rows 8/13: the authoritative record reset is recorded INCOMPATIBLE (overlay folding preserves lower-layer records) and complete destructive intent UNRESOLVED at the pin. This change ships decision data and local tests regardless — that is exactly the honest posture the design mandates ("restricted execution-time rejection supplies the missing default-deny boundary") — but no mock, fixture, or local suite may be cited as clearing either verdict, and neither native enforcement nor a working reset is claimed.
