## Why

Design §7 "Readiness and registry changes" makes the restricted boundary operational only when the synchronous `tool_call` enforcement handler installed during trusted-module loading actually *decides* every restricted call: "Check the live tool's origin on every restricted call. Operator MCP registration and refresh can occur after startup and must not bypass this check." Row 13 installed the policy-free handler SLOT and the readiness signal around it, and 14a shipped the pure decision tables (inventory allow/default-deny, live-provenance admit/deny, alternate-(capability,route) blocking, exact-key record interpretation, destructive conformance consumption, MCP admission) — but 14a is inert by construction: nothing calls it. The pinned P0 evidence records the one genuinely load-bearing native fact — `extensions/runner.ts` `emitToolCall` blocks handler errors/timeouts at execution time — so the wiring of these decisions into that handler is the operative restricted execution-time boundary, and until 14b lands, every restricted tool call runs unguarded while the tables sit unused.

## What Changes

- **The enforcement handler wired into row 13's slot**: in the row-12/13 trusted-extension module tree, `enforcement.ts` supplies the `tool_call` handler body the synchronously-registered slot dispatches to, installed during the same synchronous module-load sequence. On every restricted call it calls 14a's decisions — `tool-inventory.ts` (allow/default-deny over the complete pinned inventory), `tool-provenance.ts` (admit/deny against the tool's CURRENT recorded origin — name-match structurally insufficient, stale-epoch re-observe denial), the alternate-(capability,route) blocking table, and `destructive-decision.ts` (row-5 shared conformance consumption) — plus `approval-records.ts` advisory interpretation. The wiring adds zero decision logic: it composes 14a exports, and any new decision would force a revisit of 14a's table.
- **Consulted on EVERY restricted tool call, not a startup filter**: the handler runs per call including tools that appear mid-session (dynamic registrations, recovery re-discovery); there is no one-shot filtered registry snapshot, no path by which a call bypasses the decision, and a handler error or timeout fails the call closed (the pinned `emitToolCall` semantics row 13 documented for its SIGNAL now carry real denials).
- **Denied calls yield a fail-closed, bounded, non-secret-leaking error** observable to the client through the pinned tool-call-error surface: one bounded machine-readable reason from 14a's vocabulary (`rejected_tool_inventory`, `rejected_tool_provenance`, `rejected_alternate_route`, `rejected_approval_record_survivor`, `rejected_destructive_*`) or a wiring-level `rejected_enforcement_seam`, naming capability/route/origin category/fixture-class never file content, never credential, secret, token, or raw tool payload.
- **Post-start MCP registry-refresh admission without elicitation or one-shot ack**: when operator/client-owned MCP tools register or refresh AFTER startup, the wiring advances the registry epoch from the live tool-metadata observation, re-observes provenance (stale-epoch records deny), and re-invokes 14a's MCP-admission decision for the fresh epoch — no generic human-elicitation/form UI (design §3 non-goal), no one-shot acknowledgement. Refreshed tools that fail admission stay denied; row 13's readiness reset on refresh stands and is never bypassed by the wiring.
- **No clamps wired for native-YOLO sessions (D6)**: the handler body is registered/consulted ONLY in the restricted process; the native-YOLO launch (row 8/9's yolo overlay, no `--trusted-extension` restricted policy) registers no restricted `tool_call` policy, and OpenCode loads no extension at all.
- **Honesty: fail-closed at every unresolved inherited seam, markers carried**: MCP admission basis `needs-mechanism-audit`/`candidate-to-verify` (P0 has no MCP boundary row), readiness `ReadinessChannel` UNIMPLEMENTED (row 13's establishment seam resolves `NotReady`), record reset INCOMPATIBLE (row 8/P0 folded-overlay survival), destructive-intent decoding UNRESOLVED (row 14a/P0: undecodable native-shaped destructive input yields the shared fail-closed verdict). The wiring exposes `enforcementWiringGates` with `userDecisionRequired: true` mirroring rows 8/12/13/14a, and NEVER manufactures a passing admission/readiness/grant to make a fixture green: the wiring's own allow path is exercised only through labeled synthetic fixtures.
- **Unit/mock tests validate the WIRING decisions only**: a denied-tool fixture reaches the fail-closed bounded error; provenance is consumed LIVE (a registry mutation between calls changes the decision — no caching); post-start refresh re-admits on fresh epoch and rejects untrusted refreshes; the YOLO process registers no handler; OpenCode has no extension handler; every seam-fixture fails closed with its marker. Tests NEVER assert or imply that the native OMP binary invokes the handler, honors a denial, or enforces anything — real-runtime handler invocation stays on the user's checklist (design §15).
- Explicit non-goals (owned elsewhere, named): the decision tables themselves (14a `define-omp-restricted-tool-decisions` — landed, consumed read-only); readiness channel/identity binding + first-prompt gate (`gate-omp-policy-readiness`, row 13 — landed; the signal is consumed, never re-gated, never re-established here); pre-import exclusion + critical-skill selection internals (`guard-omp-executable-discovery`, row 12 — landed, consumed); command-path canonicalization (`harden-acp-command-path-gate`, 14c — landed, independent; the bash allow row keeps delegating to the existing common command policy); restricted LSP disablement (row 15); transport (rows 17–19 — 14a's `allow-gated-pending-adapter` rows fail closed in this wiring until those adapters land, never silently allowed); packaging (`package-pinned-omp-runtime`, row 20); destructive normalizer (row 5, consumed via 14a); P0 contract redefinition.
- No new `config.yaml`, `.env`, or Helm field: every input is 14a module output, row 12/13 module state, and the pinned registration/tool-metadata surfaces. `config.example.yaml`, `.env.example`, and `helm/values.yaml` remain intentionally unchanged; if implementation surfaces any new field, this change synchronizes all three itself.
