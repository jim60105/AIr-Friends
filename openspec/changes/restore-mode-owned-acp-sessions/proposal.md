## Why

`reconnectAndResumeSession()` today respawns whatever process its own connector options describe, restores only the session cwd on the gate context, and returns `true`/`false` — it has no notion of which permission mode or process/state namespace actually owns the session (design §5: "Reclaim, restart, and `session/load` must retain and verify that namespace. Do not accept an opposite-mode session merely because the agent can find its ID elsewhere"). With OMP's mode-split pools landed (row 10), a naive recovery could respawn a session into the wrong mode's state root, load a session belonging to the opposite mode (restricted history inside a native-YOLO process or vice versa), or resume prompting with another session's gate context. Row 11 makes recovery in `AgentConnector` and the orchestrator's single reconnect call site **original-mode, same-namespace, gate-context-preserving, fail-closed, and isolated** — consuming row 10's ownership record read-only and row 6's load-cache/stable-first config logic unchanged.

## What Changes

- **Recovery targets the recorded acquisition context.** Crash reconnect AND `session/load` SHALL recover the session against the ownership record row 10 wrote at acquisition — the ORIGINAL permission mode, process/state namespace, absolute cwd, and operator MCP definitions — and the respawn SHALL happen into the SAME mode's pool entry and state namespace. No recovery path SHALL spawn or reuse an opposite-mode process, and no recovery path SHALL re-resolve the mode (the recorded values are the recovery target).
- **Ownership verification before any teardown (fails closed).** Before `disconnect()`/respawn/load, recovery SHALL verify the recovered session against the ownership record: a session whose recorded mode/namespace does not match the recovery context — including loading an opposite-mode session — is an OWNERSHIP VIOLATION, not a recovery fallback and not a silent cross-mode load. Both directions are explicit failures: a restricted recovery context SHALL NOT load a native-YOLO-owned session, and a native-YOLO recovery context SHALL NOT load a restricted-owned session. A violation aborts that session's recovery WITHOUT touching the opposite mode's live process or lease and WITHOUT the existing "connection died and agent does not support session resumption" session-loss message being reused to mask it (a distinct bounded ownership-violation error).
- **Config restoration consumed, never forked.** After a successful same-mode load, the canonical config-options cache SHALL be restored from the `session/load` response and the requested model/reasoning SHALL be reapplied through the SAME stable-first logic — i.e., row 6's `reconnectAndResumeSession` load-cache restoration and its optional `reasoningEffort` parameter. This change WIRES those into every recovery call site with the session's resolved reasoning effort supplied; it adds NO matching/flatten/alias logic of its own and does not edit row 6's decision module.
- **Per-session gate context restored and re-registered before resuming prompting.** Recovery SHALL re-establish the recovered ACP session id's OWN filesystem/permission gate context (cwd, owning skill session id, per-session yolo/write flags — design §10 step 4: "do not use another session's fallback context for an unknown session ID") on the fresh client and register it before any re-issued prompt or continued wait; other sessions' cached gate contexts are replayed as today but never substituted for a session whose own context cannot be established (that is a gate-context restore failure → fail closed for that session).
- **Explicit row-13 attach point.** Recovery ends with a named readiness seam — gate context restored → [restricted readiness verification hook] → resume prompting. This change RESTORES the context and DEFINES the hook position; it implements NO readiness check and gates NO prompt on readiness (authenticated readiness + deny-until-ready is row 13). The boundary is stated in code comments, delta spec, and docs: restore-context yes, gate-prompt-on-readiness no.
- **Failures stay isolated (design §13).** Ownership violation, load failure, post-load model catalog miss, and gate-context restore failure each remain inside the affected session's existing per-session error handling: no retry across modes, no opposite-mode fallback, no dropping of the failed session's gate context to force progress, no effect on other sessions' gate contexts, gate-context replays, leases, or processes.
- **No new configuration, environment, or Helm field.** Recovery inputs come from the existing ownership record, session state, and operator MCP configuration; `config.example.yaml`, `.env.example`, and `helm/values.yaml` remain intentionally unchanged (if any implementation surfaces a new field, all three synchronize in THIS change).
