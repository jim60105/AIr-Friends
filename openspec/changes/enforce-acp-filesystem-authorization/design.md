## Context

See `proposal.md` — Why/What/Impact. This is the consumer cutover for two finished libraries plus the P0 compatibility verdict: `src/acp/filesystem-roots.ts` (contextual expansion, canonical root/target observations, fail-closed reasons, read-only trusted-skills role) and `src/acp/filesystem-access.ts` (root-capability, no-follow, descriptor-only UTF-8 read/overwrite/exclusive-create with named access reasons). Both are observations/IO, never grants.

Today `src/acp/client.ts` decides everything lexically and performs the IO itself: `resolveSessionPath()` expands `$TMPDIR`/`$SESSION_ID`/`$AGENT_WORKSPACE` against the session gate context, `isPathAllowed()`/`isAgentWorkspacePath()`/`isWithinTmpDir()` apply `resolve()`+`startsWith()` containment, and the callbacks finish with `Deno.readTextFile`/`Deno.writeTextFile`. `writeTextFile` re-applies a *partial* copy of the restricted write gate (shared-workspace `canWriteAgentWorkspace` + extension) so it survives without a preceding `requestPermission`, but nothing else in the restricted write policy exists independently of that request: an in-workspace ordinary target that is not shared/TMPDIR is accepted by the callback whenever it is lexically inside the session workspace, and the same target reaches the callback at all only because the agent may call it directly. Restricted read is workspace/shared containment plus the `.jsonl`/`.md`/`.txt` allowlist; there is no read route to the deployment-owned skills root, while `requestPermission` auto-approves *skill reads* by matching `locations` against `$HOME/.agents/skills` and `join(Deno.cwd(), "skills")` — name/HOME-derived trust with no provenance, no canonical identity, and no write/read linkage.

Per-session facts arrive through `SessionGateContext` (`cwd`, `shellSessionId`, `yolo`, `canWriteAgentWorkspace`, `allowedWriteExtensions`) registered by `AgentConnector.setSessionGateContext()`/`ChatbotClient.setSessionContext()` from `session-orchestrator.ts` (message/spontaneous/lurk/summary, self-research, memory-maintenance, dry-run paths) and re-applied after reconnect; the Skill API staging directory `{cwd}/tmp/{shellSessionId}` is provisioned by the orchestrator before the session runs (`Deno.mkdir(..., {recursive:true})`), and neither write sink creates parents. Denials are recorded through `recordPermissionRejection()` into a bounded ring (10 entries, 200-char sanitized fields) consumed by the missing-reply retry prompt, and mirrored to the audit writer with a machine-readable reason.

Pinned platform behavior consumed rather than re-derived: ACP SDK `0.14.1` callback shapes (`ReadTextFileRequest`/`WriteTextFileRequest` carry `sessionId` + `path`(+`content`) and no creation/truncate intent), OpenCode `1.18.21` read/write/apply_patch delegation shapes, and OMP `v18.6.1` `acp-bridge.ts` client-fs behavior (the bridge routes native read/write through the same `fs.readTextFile`/`fs.writeTextFile` request methods and only falls back to native IO when the client did not declare `fs` capability, which `agent-connector.ts` advertises as `readTextFile: true`/`writeTextFile: true`). No new API method is invented on either side.

## Goals / Non-Goals

**Goals:** Every ACP filesystem callback decision is made on canonical physical observations, executed only through the protected operations, and authorized by an agent-generic policy that needs no preceding permission request — restricted narrow (own staging, or shared with authorization + extension), YOLO broad (workspace/shared membership), read-only trusted-skills exception with provenance, one bounded reason per denial. The replaced lexical predicates and the name/HOME skills rule are gone from the sink path, with callers, registration, tests and docs consistent.

**Non-Goals:** The libraries' own behavior (root roles, syscalls, ABI, replacement semantics), destructive-target normalization/shapes, the generic-command argument gate, restricted tool inventory/provenance/default-deny, readiness and prompt gating, native OMP delegation/discovery, recursive safe directory materialization, staging relocation, Skill API handler/Skill-API payload checks, dashboard/memory/workspace APIs, pool/mode/state allocation, absolute staging prompt recipes, network/transport, packaging, and any new configuration/environment field.

## Decisions

### 1. One focused sink-policy module; the client wires, the policy decides

Create `src/acp/filesystem-policy.ts` (plus its unit test) holding the agent-generic decision, and keep `src/acp/client.ts` responsible for protocol wiring, activity/audit/rejection bookkeeping and error mapping. Proposed AIr-owned signatures — not OMP/ACP wire APIs:

- `buildSessionFilesystemContext(gateCtx, deployment): Result<FilesystemSessionContext>` assembles the predecessor's required context: exact ACP session id, owning Skill API session id (the existing `shellSessionId`), absolute `cwd`, the explicit canonical staging path `{cwd}/tmp/{shellSessionId}`, optional configured shared Agent workspace, optional deployment-owned trusted-skills provenance, and a context generation. Process TMPDIR, `processTmpDir`, `xdgDataHome` and `PI_CODING_AGENT_DIR` are deliberately **not** inputs; they never grant a root, matching the predecessor contract.
- `authorizeFilesystemRead({roots, target, policy})` and `authorizeFilesystemWrite({...})` return either `{role, access: "read"|"overwrite"|"create", useTrustedReadRule}` naming exactly one role the observation already carries, or one bounded `FilesystemDenial` reason. They never touch the filesystem, never widen a role, never fall back, and take no path string (observations in, decision out) so rows 5/14 can reuse the same classification.

`readTextFile`/`writeTextFile` then follow one shape: expand/resolve with the predecessor helper → `canonicalizeSessionRoots` → `resolveFilesystemTarget` → policy decision → `readCanonicalTextFile`/`writeCanonicalTextFile` with the selected role. Any `Result` failure at any step is a denial with the mapped reason and zero content IO; there is exactly one code path that can perform content IO, which is what makes "no obsolete bypass remains" checkable by reading the callbacks. `resolveSessionPath()` keeps existing token semantics by delegation to the predecessor's expansion, never a second copy.

Roots are observed per callback rather than cached across callbacks: root construction is metadata-only, sessions are long-lived over pooled processes, and staging/lifecycle state legitimately changes between callbacks. Registration, not caching, owns staleness (§5).

### 2. Restricted write authorization is independent of `requestPermission`

Shared decision table, applied identically whether the agent went through `requestPermission` (`kind: "edit"`/legacy title shapes) or called `writeTextFile` directly:

| Observation (restricted) | Result |
| --- | --- |
| Target holds the requesting session's own canonical staging role | allow (`overwrite`/`create` per target existence), no extension filter |
| Shared Agent workspace role | allow only with `canWriteAgentWorkspace === true` **and** an allowed write extension; otherwise `rejected_agent_workspace_write_unauthorized` / `rejected_write_extension` (existing reasons preserved) |
| Workspace role only (ordinary user-workspace file that is not the session's staging root) | deny `rejected_workspace_write_restricted` — including an otherwise-allowed `.md` |
| Trusted-skills role | deny `rejected_trusted_skills_read_only`; no write exception, in any mode |
| No applicable role, or observation/access failure | deny with the mapped outside-root/observation/access reason; never path IO |

Ordering is deliberate: staging/shared/extension reasons are evaluated before the generic in-workspace denial so existing retry-diagnostics text stays meaningful. Existing reasons `rejected_write_path_outside_workspace`, `rejected_agent_workspace_write_unauthorized` and `rejected_write_extension` keep their codes, so retry-prompt and audit consumers, and rows 5/14/22's expectations, do not churn. Staging grants are the *physical* staging role only: a link spelled inside staging that resolves elsewhere, a sibling session's staging root, an ordinary workspace directory and a process-state alias cannot produce it (the predecessor's role decision plus row 3's containment enforcement do this, not a prefix test).

`requestPermission`'s edit/write branch keeps its existing approval/denial shape for staging and shared targets but no longer needs to *cause* safety: the write itself is safe regardless of the request outcome, per design D9. Complete destructive shapes stay out of scope (§8).

### 3. YOLO keeps broad containment, gains no restricted clamp and no new hole

For YOLO the decision is: workspace or shared role ⇒ allow, with no staging-only rule, no `allowedWriteExtensions` filter, no `canWriteAgentWorkspace` requirement, and no LSP/tool/command denial — the existing YOLO test expectations (any extension in the shared workspace, any extension anywhere in the workspace) survive unchanged. YOLO does **not** relax: external/sibling escape denial, physical-not-lexical membership, the trusted-skills read-only rule (row 3 already rejects a write selecting that role, and the policy denies it earlier with a named reason), and observation/access failures. Documentation states the boundary honestly: these callbacks constrain ACP-delegated file operations only; a state file already inside the permitted broad workspace is not specially denied in YOLO, and native non-ACP execution is not covered.

### 4. Read policy: existing rule preserved, trusted root added separately

- Workspace/shared: physical membership plus the unchanged `.jsonl`/`.md`/`.txt` read-extension allowlist and unchanged case-insensitive extension semantics. No read extension is broadened.
- Trusted skills: a target holding the `trusted-skills` role is admitted **by owned-root membership** rather than by the workspace extension allowlist, because the owned root is deployment-owned content that legitimately includes `SKILL.md` and `.ts` scripts; the exception is root-scoped, read-only, and does not authorize writes or arbitrary external files. It requires deployment-owned provenance (predecessor `CriticalSkillContract` root/source identity, canonical root agreement, disjointness from writable roots) and current-generation currency; a stale generation, ownership mismatch, escaping link or writable-root overlap yields the specific trusted-identity failure and no fallback to another readable role. Reads of a path that also happens to live in the workspace keep ordinary workspace rules; a workspace file can never become trusted by name.
- `requestPermission`'s skill-read branch is replaced by the same classification: approve a `kind: "read"` request only when its `locations` resolve (via the same context/observation path) to the trusted-skills role, keeping the existing `skills_directory_access` audit reason. The `$HOME/.agents/skills` + `join(Deno.cwd(), "skills")` `isWithinDir` branch and its `Deno.env.get("HOME")` default are deleted, removing a rule that could approve any HOME-anchored path. Consequence, stated explicitly: OpenCode's ambient HOME-discovered and `npx skills add`-installed skill copies are no longer auto-approved as reads; readable skill content comes from the deployment-owned canonical root the lifecycle owner supplies as provenance (same canonical owned skills directory `agent-factory.ts` already uses for the retry-prompt `SKILL.md` bodies). Widening the trusted source set — e.g. certifying externally installed skill roots with real provenance — is row 12's provenance/discovery question and P0's critical-skill contract, not this change; if that boundary is unresolved, application of this change remains gated rather than being satisfied by name/HOME matching.
- `AgentConnector`'s advertised `fs` capability (`readTextFile`/`writeTextFile: true`) is unchanged, so pinned OMP/OpenCode continue delegating rather than using native IO; the pinned bridge only falls back to native file IO when the client did not declare the capability, which would be a silent loss of these boundaries. Any future capability change is a separate, reviewed decision.

### 5. Trusted-skills provenance and context generation travel with the existing per-session gate context

Extend the existing `SessionGateContext` and its registration plumbing instead of adding a second session registry:

- `trustedSkills?: TrustedSkillsSource` — deployment-owned canonical owned root plus the predecessor contract's root/source identity, supplied by the lifecycle owner (bootstrap/orchestrator composition root) and passed through `AgentConnector.setSessionGateContext()` exactly like `canWriteAgentWorkspace`. Untrusted callers cannot register it: it is a trusted-input field sourced from deployment configuration and P0's contract, never from model/tool content, and it is validated by the predecessor helper rather than trusted on arrival. Absent provenance simply means no trusted role exists.
- A `generation` the `ChatbotClient` assigns when it accepts a context registration (per ACP session id, monotonic per client), used as the predecessor's context generation so an observation cannot be replayed after re-registration/reconnect. `setSessionContext` merging stays as-is; the sink path only uses the currently registered context, and an unknown ACP session id has no filesystem context (no daemon/first-session fallback), so an unregistered session is denied rather than falling through to `config.workingDir`-derived lexical containment. Removing that fallback on the sink path is part of the cutover; the generic-command branch's existing behavior is untouched (§8).

`SessionGateContext` remains the single registration surface, so all current entry points (message, spontaneous, lurk, self-research, memory-maintenance, summary, dry-run, dashboard, reconnection reload loop, `session/load` resume) inherit the new fields by passing them through, and row 11's restore path keeps ownership of re-establishing them.

### 6. Bounded, specific denial diagnostics

Each sink denial records exactly one bounded reason, reusing `recordPermissionRejection()` (existing truncation/sanitization and audit mirroring) and `acp.RequestError` with a static message — never file content, secret, raw platform error or unbounded agent text. Preserved: `rejected_write_path_outside_workspace`, `rejected_agent_workspace_write_unauthorized`, `rejected_write_extension`, read-extension rejection (thrown, not buffered, exactly as today), `skills_directory_access` (approved), `rejected_edit_write`, `rejected_unknown`. Added, as finite named reasons for the new decisions: `rejected_workspace_write_restricted` (restricted ordinary user-workspace target), `rejected_trusted_skills_read_only`, `rejected_trusted_skills_identity` (provenance/generation/containment failure), `rejected_filesystem_path_unavailable` (canonical observation failure: outside-roots, symlink escape, dangling/loop, wrong type, path-changed, unresolved token, invalid context), `rejected_filesystem_access` (secure-access failure: parent-missing, root-unavailable, unsafe traversal, replacement/path-changed, IO failure, unsupported platform/capability), and `rejected_filesystem_context` (missing/unregistered session context). The mapping from predecessor reason codes to these is a table in `filesystem-policy.ts` plus the documented reason table, one reason per denial, no contradictory double-booking (the existing "don't record a second `rejected_edit_write`" rule is preserved). A missing/unprovisioned staging directory is surfaced as `rejected_filesystem_access` with `parent_missing`/`root_unavailable` preserved for logs; the sink never calls `mkdir` to paper over it (row 3 forbids recursive materialization and lifecycle owns provisioning), and the docs name that operator-visible failure.

### 7. Clean cutover: delete the replaced logic, keep the unrelated rules

Remove from `src/acp/client.ts`: the callbacks' `resolveSessionPath`/`isPathAllowed` containment use, `isAgentWorkspacePath`, `isWithinTmpDir`, the private `isWithinDir` sink uses and the HOME/`Deno.cwd()` skills branch. `isWithinDir` itself stays exported while the unchanged generic-command path-argument gate (its `allowedDirs`/`dataRoot`/tool-output uses) still needs it; removing the *sink* uses without pretending the command gate is hardened is the honest boundary — the command argument gate becomes a named, documented remaining lexical path owned by row 14 (`enforce-omp-restricted-tool-policy`), and the exported helper's remaining callers/tests stay green. `skills/lib/payload.ts` has its own independent `isWithinDir` and payload containment; that Skill-API authority is untouched. `extractPathsFromRawInput()`, `isEditWriteRequest()`, the read/write extension allowlists, `hasAllowedWriteExtension()` and the registered-skill/execute-whitelist branches remain — their classification role is unchanged, only the physical decision underneath them changes. Tests that assert the removed behavior are replaced rather than kept as obsolete bypasses: the "arbitrary in-workspace file write succeeds (non-agent-workspace)" case flips to the restricted denial plus its YOLO counterpart, and the `$HOME/.agents/skills` auto-approve and audit cases move to provenance-backed owned-root cases (with an escaping/unowned-root denial and a no-provenance denial).

### 8. Explicitly unchanged, so the slice stays one engineer-day

No change to: destructive edit/write shape handling, titles, multi-target or incomplete-intent behavior (row 5); generic-command tokenization, operator checks, argument path gate, skill auto-approve list and free-text-flag rejection; skill registry/MCP/session lifecycle, model/reasoning configuration; `docs/AGENT_PERMISSIONS.md` Layer-2/5 descriptions except the parts Layers 3/4 and the reason table actually change; `config.example.yaml`, `.env.example`, `helm/values.yaml` (no new field: the trusted-skills root is the existing deployment-owned canonical skills directory plus contract-internal provenance, not operator configuration). No shim, alias, feature flag, or "old behavior if observation fails" branch.

## Risks / Trade-offs

- **Restricted in-workspace writes stop working** → intended per design §8 step 6; staging root + shared/authorized-extension writes cover the real skill payloads, and the denial reason names the fix. The legacy-success test is replaced, not left passing.
- **HOME-discovered skill reads stop being auto-approved** → intended (name/HOME matching was the bypass); owned-root provenance is the replacement. If P0's critical-skill selection boundary is unresolved, this change's application stays blocked rather than reverting to name matching.
- **Contained symlinks now fail on adoption** (row 3's supported backend rejects them, even inside a root) → explicit named denial + documentation; no hidden raw-path fallback, and the root-alias case remains usable through canonical identity.
- **Platform capability becomes load-bearing** — an unsupported libc/kernel/seccomp environment fails closed for both agents rather than silently using lexical path IO. That is the approved trade: a named `rejected_filesystem_access`/`unsupported_platform` outcome and an application blocker instead of a weaker portable fallback.
- **Two sinks can still diverge if the shared decision is not used** → mitigated by one decision table in `filesystem-policy.ts`, one content-IO call site per callback, and tests asserting identical outcomes through `requestPermission` and a direct callback.
- **Shared-file contention** (`client.ts`, `types.ts`, orchestrator registration points, permissions docs, changelog, `acp-integration` spec) → apply predecessors first, this row before rows 5/13/14/16, and one integration owner for subsequent `client.ts` edits.
- **Mock-only evidence** → temp-filesystem and mock results certify client decisions only, never native OMP delegation, immutable extension paths, deployment libc/seccomp behavior, architecture images or bwrap; the user's runtime checklist stays unverified and predecessor blockers stay open.
